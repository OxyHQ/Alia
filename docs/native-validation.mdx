# Native validation (Android)

[#608](https://github.com/OxyHQ/Alia/issues/608) asks for the refactor to be
checked on a device, not only in a browser. The web harnesses
([visual](./visual-baseline.mdx), [runtime](./runtime-baseline.mdx)) cannot see
what only a device has: a status bar lying over the app, a software keyboard, a
system permission dialog, a microphone. This page is one pass of that on
Android, on 2026-09-25, against `feat/608-integration` at `a83d0e5f` plus the
fixes below (branch `chore/608-android`).

**Read [§6](#6-what-this-does-not-cover) before quoting it as coverage.** The
first pass (§1–§5) is one emulator, signed out. A second pass on a physical
Pixel 8a ([§7](#7-second-pass-pixel-8a)) fixed and checked the keyboard defect
from §4.4, signed in. A third, visual pass on the same Pixel 8a
([§8](#8-third-pass-visual-qa-on-the-pixel-8a)) went through insets, the
keyboard, menus and sheets in both themes and at the largest font; **its first
finding is a crash at launch in Bloom that is not fixed yet (§8.2)**. There is
no iOS here at all.

## 2. Commands

```bash
cd packages/app
CI=1 bunx expo prebuild -p android --clean        # android/ is gitignored; always regenerate
cd android
ANDROID_HOME=~/Android/Sdk NODE_ENV=production \
  ./gradlew assembleRelease -PreactNativeArchitectures=x86_64
# first build 3 min 9 s from clean; later ones 1.5–2 min

adb -P 5041 install -r app/build/outputs/apk/release/app-release.apk
adb -P 5041 shell pm clear onl.alia.app           # signed-out, first-run state
adb -P 5041 shell am start -W -n onl.alia.app/.MainActivity
adb -P 5041 exec-out screencap -p > shot.png
adb -P 5041 logcat -v time > logcat.txt
```

Prebuild prints one warning worth knowing: `userInterfaceStyle: Install
expo-system-ui in your project to enable this feature`. The app's own dark mode
works without it (§3); what is missing is the native window background
following the theme before JS runs.

Taps were `adb shell input tap` at coordinates read off the screenshots:
`uiautomator dump` cannot be used, because the ambient field never lets the UI
go idle.

## 4. What the device found, and what was fixed

### 4.1 Status bar icons invisible — fixed

Nothing rendered an `expo-status-bar` `<StatusBar>`, and the app is drawn edge
to edge, so the icons stayed light over Alia's light surface: the clock and
battery were close to invisible. `app/_layout.tsx` now renders
`<StatusBar style={isDarkColorScheme ? 'light' : 'dark'} />`, following the
theme Alia resolved (which can differ from the OS's, since the drawer has its
own switch). Verified in light and dark.

### 4.2 Shell under the status bar; menu button dead on most of its area — fixed

Bloom's `AiChatShell` takes no safe area, and the chat routes and Settings took
none either (the layout's `SELF_INSET_ROUTES` exempted them, but nothing in them
applied the top inset). On Android the frame, the header and the drawer therefore started
at y = 0, under a status bar 136 px tall. The menu button's centre was at
y ≈ 110, inside the status bar's window, which takes the touch: **a tap on the
button's upper two thirds did nothing**; only its lower edge opened the drawer.

`app/(app)/_layout.tsx` now wraps the shell once, on native only, in a view
padded by `insets.top`, and no route pads itself again (`SELF_INSET_ROUTES` is
gone). Web is untouched: its insets are zero and it scrolls the document, which
a wrapping flex view would break. The strip above shows the root background,
which is the shell's own surface colour. Gate:
`__tests__/native-system-bars.test.ts`.

### 4.3 Composer behind the keyboard — fixed (regression from 4.2)

Moving the shell down exposed an assumption in `ChatWorkspace`: its
`KeyboardAvoidingView` (keyboard-controller) computes the overlap from its frame
**relative to its parent**, as if it started at the top of the screen. With the
shell a status bar lower, the composer stopped 136 px short and its bottom half
sat behind the keyboard. It now passes `keyboardVerticalOffset={insets.top}`.

keyboard-controller's own `automaticOffset` (measure the view on screen) was
tried first and rejected: it measures asynchronously, and on a freshly cleared
app it lost the race to the first layout in two runs of three, leaving the same
gap. The offset is deterministic; three runs from a cleared app all showed the
whole composer. Gate: `src/features/chat/ui/__tests__/chat-workspace-background.test.tsx`.

### 4.4 After a sheet or popover, the composer no longer follows the keyboard — fixed (Alia and Bloom)

Signed out, press send: the Oxy sign-in sheet (a Bloom `BottomSheet`, which is a
React Native `<Modal>`) opens. Close it and the keyboard comes back, but the
composer does not rise; it stays behind the keyboard. From then until the app is
restarted, **every** focus of the composer has the same problem. At the moment
the sheet opens, logcat shows one copy of this per keyboard-controller provider:

```
E/unknown:UIManagerHelper: Unhandled SoftException
java.lang.IllegalStateException: Fabric View [-1] does not have SurfaceId associated with it
  at ...FocusedInputObserver.<init>(FocusedInputObserver.kt:46)
  at ...KeyboardAnimationCallback.<init>(KeyboardAnimationCallback.kt:129)
  at ...modal.ModalAttachedWatcher.onEventDispatch(ModalAttachedWatcher.kt:58)
  at com.facebook.react.views.modal.ReactModalHostManager...
```

The exception itself is harmless (the observer falls back to surface −1). The
cause is next to it in `ModalAttachedWatcher` (keyboard-controller 1.21.9, and
unchanged in 1.22.5): when a `<Modal>` shows, **every** `KeyboardProvider`'s
watcher suspends its own main-window keyboard callback, then calls
`dialog.setOnDismissListener { … suspend(false) }`. A dialog keeps only the
**last** listener. With two providers or more, the dialog's dismissal resumes
one of them, and the others stay suspended until the process dies, taking every
`KeyboardAvoidingView` under them along.

Alia had three: `OxyProvider`'s `KeyboardBoundary`, Alia's own in
`app/_layout.tsx`, and the one Bloom's `BottomSheet` re-established inside its
`<Modal>`. That is why removing only Alia's (tried in the first pass) did not
fix the sign-in sheet: the Oxy provider and the sheet's still made two. It is
also why the defect does not need the sign-in sheet. Signed in, the model
picker (a Bloom popover in a `<Modal>`, two exceptions) and the Oxy account
sheet (three) do the same.

Fixed at both ends, so there is exactly one provider, `OxyProvider`'s:

- **Bloom 4.22.1** ([OxyHQ/Bloom#203](https://github.com/OxyHQ/Bloom/pull/203)):
  the sheet mounts no provider of its own. React context crosses the `<Modal>`,
  and the root provider's watcher carries the dialog window's keyboard events
  to the root provider's view, which is where the sheet's handler is
  registered.
- **Alia** mounts none (`app/_layout.tsx`; `@/shared/platform/keyboard` no
  longer exports one). Gate: `__tests__/one-keyboard-provider.test.ts`. It
  checks Alia's source, that `OxyProvider` mounts the one, and that the
  installed Bloom sheet adds none.

A `Keyboard.dismiss()` before `signIn()`, tried in the first pass, only hid the
bug. Alia carries no workaround.

### 4.5 Smaller things seen

- **Reanimated warnings.** 273 `W/Reanimated: synchronouslyUpdateUIProps failed
  for tag …` (`RetryableMountingLayerException: Unable to find
  SurfaceMountingManager`) in one session, in bursts at launch and when the
  welcome hands over to the chat: animated props written to views already
  unmounted. Warnings only; nothing visible.
- **Signed-out Library called the API — fixed.** Opening Library signed out
  logged `E/ReactNativeJS: 'Error loading library files:', [AxiosError: Request
  failed with status code 401]`. The page now loads the files only for an
  account, and signed out its "Add files" opens sign-in instead of an upload the
  API would refuse (#608 §3.2). An audit of the other screens a visitor can
  reach found the same pattern in the agent editor (skills, connectors,
  library), the approvals poll (every 60 s), an agent's threads and the teams
  list; all are gated now. Gates: `app/(app)/__tests__/library-drawer-toggle.test.tsx`,
  `src/features/agents/runtime/__tests__/signed-out-requests.test.tsx`. Still
  asked signed out, and left alone: `useAgentThread` (`/@handle`, where the
  401 renders "not found" and gating would leave the page spinning) and
  `useSessionActivity` (link-only).
- **Sign-in sheet foot — fixed in Bloom.** It is not a language selector. It is
  the "Having trouble?" accordion (`@oxy.so/services` `TroubleDisclosure`),
  truncated to "Having" and painted under the gesture bar. Both are Bloom's:
  4.21.0 gives every bottom-placement `Dialog` a spacer as tall as the bottom
  safe area, and trigger labels keep their width. Nothing in `@oxy.so/services`
  changed. On the Pixel 8a with 4.22.1 the Oxy account sheet's last row sits
  clear of the gesture bar. On 4.20.0 its "Switch account" accordion was also
  drawn as a huge circle.
- **`action` tone is green.** "Get started", "Add files" and the send button are
  green on a purple app. That is Bloom's `purple` preset, whose action colour is
  derived as a complement by design — not the device's Material You palette
  (Alia does not use `adaptive`). A design call, not a defect.
- **Splash under dark icons.** For the fraction of a second the splash is still
  up after JS has run, the status bar icons are already dark for the light theme
  over the dark splash.
- **Return inserts a newline.** On the soft keyboard ↵ adds a line; sending is
  the send button. Expected for a multiline field on a phone.

## 5. Audio

- **Dictation** (the composer's microphone, which works signed out): the system
  asks for the microphone; after "While using the app" the status bar shows the
  green microphone chip, `dumpsys audio` shows an active `VOICE_RECOGNITION`
  session for `onl.alia.app` at 16 kHz mono, the button turns into a level
  meter, and after about 8 s of silence the session ends and the draft is left
  as it was. The emulator's microphone is the host's through WSLg PulseAudio,
  and nothing could speak into it, so **recognition itself was not validated**:
  the microphone opens and closes cleanly, nothing more.
- **Read aloud (TTS)** needs an assistant message, and a signed-out send only
  opens the sign-in sheet, so it is **not reachable signed out and was not
  validated**; neither was the speaker path through WSLg.
- **Voice mode** (calls) needs an account and a plan: not validated.

## 6. What this does not cover

- **iOS.** Not on this machine; it needs a Mac with Xcode. Nothing here says
  anything about iOS, where the keyboard avoidance runs a different behaviour
  (`padding`) and the safe areas differ.
- **Signed in.** The first pass used no account; the Pixel 8a pass (§7) was
  signed in but only exercised sheets, the picker and the composer. Streaming turns, tools, the thread with
  real messages, history, read aloud, calls, notifications, attachments and the
  right-hand panel were not exercised.
- **A real phone.** The first pass is one emulator, x86_64, software GPU; §7
  adds one Pixel 8a, for the keyboard defect only. No low-end device, no
  gesture-vs-three-button navigation comparison, no tablet or foldable (on
  Android 16, large screens may ignore the portrait lock), no display cutout
  other than the Pixel 7 profile's.
- **Push delivery.** No `google-services.json` in the worktree, so FCM was not
  configured in this build.
- **The web.** Nothing here was checked on web; the web harnesses are the
  reference there. The layout change keeps web on its old path by construction
  (`Platform.OS === 'web'`), and the app's unit suite passed.

### 8.2 Open in Bloom (reported, not patched here)

Each one was seen on the device and traced to the named file of the installed
`@oxy.so/bloom` 4.23.0; none is worked around in Alia.

1. **Crash at launch for any account with a chat (P0).** `sidebar/Sidebar.tsx`
   (`contentMorph`, lines 257–261) reads `tree` inside a `useAnimatedStyle`
   worklet, so Reanimated serializes the whole tree to the UI thread — rows,
   their React elements and the conversations in their props — and dies on the
   first `Date`: `FATAL EXCEPTION … [Worklets] Cannot copy value of type Date`,
   about three seconds after `Running "main"`, on every launch. The serialized
   path (closure → tree → folders[] → items[] → `actions` element → props →
   conversation → `createdAt`) was read off the symbolicated stack. Capturing
   `const treeShown = Boolean(tree)` outside the worklet ends it: the rest of
   this pass ran on a build that swapped in that one-line change through a
   local Metro redirect, which is **not committed**. Until Bloom ships it, a
   release built from this branch crashes for every signed-in user with history.
2. **Back with the navigation drawer open exits the app.** `AiChatShell`
   registers a hardware-back handler for the panel only
   (`ai-chat/use-panel-interaction.ts`), not for the drawer.
3. **Code blocks inside a turn do not scroll sideways.** The turn's long-press
   menu wraps it in `ContextMenuTrigger`, whose `TriggerSlot` is a `Pressable`;
   on Android it keeps the horizontal pan from `CodeLines`' `ScrollView`. A
   build without the wrapper scrolled the same block.
4. **Composer toolbar overflow.** `composer-panel/ComposerPanelBase.tsx` gives
   the right group `flexShrink: 0` and `ModelPickerBase`'s trigger `flexShrink:
   0` with no `minWidth: 0`, so a long model name ("DeepSeek: DeepSeek V4 Pro
   0813") covers the + button and pushes voice off the card; at font 2.0 the
   32 px trigger also clips its text.
5. **The effort popover is drawn under the gesture bar** (not clamped to the
   bottom safe area).
6. **The thread can stop following a streamed answer.** `ScrollThread` measures
   "near the bottom" with `offset.current`, which only a scroll event updates;
   two size changes before the event that follows a non-animated `scrollToEnd`
   read a stale offset and turn the follow off for good. Alia's jump button is
   driven by the same scroll events, so it stays hidden too.
7. **The prompt does not resize for a value set from outside** (loading a
   question to edit, cancelling the edit) until it is focused:
   `ComposerPanelBase` sizes it from `onContentSizeChange` only.
8. **A bottom `Dialog` keeps its gesture-bar spacer with the keyboard up.**
9. **Settings pages are not keyboard-aware**: a field near the bottom of
   Personalization stays behind the keyboard.
10. **Sidebar rows clip their labels at the largest font.**
11. The floating chrome's scrim leaves the transcript legible behind the
    breadcrumb row (a design question more than a defect).

### 8.6 Follow-up: dictation, the agent page's Chat, dialogs' keyboard

Same phone, same day, on `fix/608-device-qa` merged forward to `d3a60b33`.
Built as in §8, with the Bloom sidebar fix of §8.2 swapped in locally for the
test only (not committed; Bloom's release carries it).

**Dictation.** Asked at run time (a probe build, not committed), the phone has
exactly one recognition service, Android System Intelligence
(`com.google.android.as`), and it reports **no language at all** — installed,
downloadable or online (`RecognitionSupport { installedOnDeviceLanguages = [],
supportedOnDeviceLanguages = [], onlineLanguages = [] }`). There is no Google
app, no "Speech Services by Google" (`com.google.android.tts`) and no Play
Store, so nothing on it can recognize speech and no locale Alia could ask for
would work; `en-US` is what it asked for, correctly. Two changes, in the SDK:

- `chooseSpeechRecognizer` asks every service which languages it recognizes,
  the default first, and uses the first that has the app's language (or
  another region of it), under that service's spelling of the tag, passing
  its package to `expo-speech-recognition`. That is what makes dictation work
  on a Pixel whose default service lacks the language but whose Google speech
  service has it. The same choice is made when a voice call connects.
