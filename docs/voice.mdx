# Voice

Alia has two voice features, and both run the same way since `@alia.onl/sdk`
8.0.0: **the device listens, the chat path answers, Oxy speaks.**

| Feature | Hook | What it does |
|---|---|---|
| Dictation | `useSpeechToText` | The composer's mic: speech becomes text in the draft |
| Voice call | `useVoiceRoom` (app: `use-voice-mode.ts`) | A spoken conversation: listen → answer → speak, with barge-in |
| Read aloud | `useTTS` | A message, spoken on request |

## Why it is built this way

Until #477 dictation posted audio to `POST /v1/voice/transcribe` and a call opened
a LiveKit room from `POST /v1/voice/token`; both reached speech providers
directly. Alia's only inference path is `Alia -> Oxy -> Kaana`
([ADR 0001](./adr/0001-alia-oxy-kaana-responsibility-boundary.md)), and Oxy serves
chat and speech synthesis but **no transcription and no realtime session**. The
two routes answered `503` from the cut-over on, and are removed. Adding those
capabilities to Oxy and Kaana is cross-repository work; recognizing speech on the
device needs none of it.

Retiring the LiveKit room, cohost and the voice-minutes allowance is a product
decision, recorded in [ADR 0013](./adr/0013-voice-runs-on-the-device-livekit-and-cohost-are-retired.md).

## Listening: on the device

`packages/alia-chat/src/lib/speech-recognition*.ts` is one contract with two
engines, picked by the bundler:

- **Web** (`speech-recognition.ts`): the browser's Web Speech API
  (`SpeechRecognition` / `webkitSpeechRecognition`). Chromium browsers and Safari
  have it; **Firefox does not**, and dictation says so instead of failing
  (`useSpeechToText().isSupported === false`, and the voice call refuses to start).
  A `getUserMedia` stream is opened beside the recognizer for the permission
  prompt, precise device errors and the level meter; it is never recorded.
- **iOS / Android** (`speech-recognition.native.ts`): `expo-speech-recognition`
  (Apple's Speech framework, Android's `SpeechRecognizer`), continuous with
  interim results and punctuation, and iOS voice processing (echo cancellation)
  during calls. It is a native module: the app lists its config plugin in
  `app.json`, which writes `NSSpeechRecognitionUsageDescription`,
  `NSMicrophoneUsageDescription`, `RECORD_AUDIO` and the Android recognizer
  visibility query — **it needs a new native build**.

The language is the app's (`packages/app/src/features/voice/model/speech-locale.ts`): `i18n.locale`,
widened to a regional tag from the device's locales when it is bare.

**Which recognizer, on Android** (`chooseSpeechRecognizer`, run once before a
dictation or a call starts). Android may have several recognition services — on
a Pixel, Android System Intelligence (on-device, only the languages whose packs
are installed) and Google's speech services — and `SpeechRecognizer` answers a
language it cannot do only by failing. So each service is asked which languages
it recognizes, the default first; the first that has the language (or another
region of it: `es-US` for `es-ES`) is used, under its own spelling of the tag.
When services answer and none has the language, dictation says so without
opening the microphone. When every service answers with no language at all,
the default is still tried, and if it refuses, the message is "speech
recognition is not available on this device", not "does not support this
language" — which is what a Pixel with no speech services and no language pack
showed (`docs/native-validation.mdx` §8.4). iOS and the web have one recognizer
and go straight to it.

**Privacy, stated plainly.** No audio reaches Alia. What the platform's
recognizer does is the platform's: Chrome's Web Speech API streams audio to a
Google service; Safari and iOS use Apple's, on-device where the device supports
it; Android uses the device's recognition service, on-device where installed.
Accuracy is the engine's too, and varies by browser, device and language.

## Answering: the chat path

A spoken turn **is a chat turn**. In the app, `use-voice-mode.ts` hands each
utterance to the conversation screen's own `sendMessage` — `POST /alia/chat` with
the open conversation, its agent, the chosen model and every tool — so a call's
turns land in the thread as ordinary messages, persisted by the server. The SDK's
default sender (`createAliaVoiceTurnSender`) makes the same request `useAliaChat`
does, on `/v1/chat/completions`.

Every voice turn carries `responseMode: "voice"`. The API layers
`prompts/voice.md` over the turn's prompt (`SystemPromptBuilder` chooses prompts by
surface, never by model): short, conversational, nothing that reads badly
aloud. Routing, tools and billing are those of a typed turn.

## Speaking: Oxy speech, sentence by sentence

Answers are spoken through `POST /v1/audio/speech` — the same route read-aloud
uses (`lib/speech-synthesis.ts` is shared) — in the product voice, `male` or
`female`; no upstream voice name is ever sent or shown. The loop synthesizes the
first sentence as soon as it has streamed, gathers later sentences into fuller
chunks, and fetches the next clip while the current one plays. Markdown, code and
links are stripped from what is spoken, not from the transcript.

**Barge-in.** The microphone stays open while Alia thinks and speaks. When the
person says two or more words that are not the answer echoing back
(`isInterruption` in `lib/voice-text.ts`), the turn is aborted — playback stops
and the chat request is cancelled — and what they are saying becomes the next
utterance.

## When speech fails

A call that cannot speak **ends, and says why** — it never listens on in
silence. When a clip cannot be made or played, the turn stops speaking (no
later sentence is played out of order), the answer finishes streaming into the
thread — the chat request is not cancelled, so the written answer is whole —
and then the call ends with a `VoiceErrorCode` the app says in its own
language (`voice.errors.*`):

| Route answer (`error.code`) | Status | Call ends with |
|---|---|---|
| `SPEECH_UNAVAILABLE` — no inference client, no speech model, no route, storage not set up, Oxy refusing Alia's authority | 503 | `synthesis-unavailable` |
| `SPEECH_LIMIT_REACHED` — rate limit, quota, spending limit, balance (`Retry-After` when Oxy gave one) | 429 | `synthesis-limited` |
| `SPEECH_REJECTED` — the model refused the voice, the speed or the text | 422 | `synthesis-rejected` |
| `SPEECH_PROVIDER_FAILED` — upstream error, timeout (504), transport, not MP3 | 502 / 504 | `synthesis-failed` |
| `SPEECH_GENERATION_FAILED` — storing or attaching the clip failed | 502 | `synthesis-failed` |
| 401, or no session token on the device (no request is made) | — | `not-authenticated` |
| The device could not play the clip | — | `not-played` |

The route's message is provider-neutral and fixed per code; Oxy's `requestId`
travels with it. On the device, `requestSpeechClip` throws a `SpeechClipError`
that keeps the HTTP `status`, the typed `code` (`null` for a network failure or
a code the SDK does not know), `retryable` and `requestId`; `useVoiceRoom`
exposes the one that ended the call as `synthesisError`.

**Server side**, `lib/synthesize-speech.ts` is the only caller of the inference
client for speech and the only reader of its error type; the route and the show
pipeline see a `SpeechSynthesisError`. It tries the speech models in the
catalogue's order ([Model abstraction](./model-abstraction.mdx)) and moves to
the next — at most three, within one 60-second budget — only when the model
itself refused (`invalid_request`, `unsupported_modality`, `model_not_found`,
`no_route_available`, `commercial_permission_denied`); every other refusal,
authentication and credit above all, fails at once. Each failed request is one
structured `speech` log record — `code`, `reason`, `status`, Oxy's
`upstreamCode` / `upstreamStatus` / `requestId` / `param`, the models tried,
the product voice and the input's length — and never the text, the user or the
conversation. Each fallback is a `warn` record of the same kind.

## When a call ends on its own

A call belongs to one conversation of one account, on the screen showing it
(`use-voice-mode.ts`). It ends — recognizer stopped, microphone released —
when that screen is covered by another route (the native stack keeps it
mounted), when the screen moves to another conversation, or when the account
changes. It never follows the person into another thread.

Dictation and a call never listen together: the call bar replaces the
composer, which owns dictation, and an unmounted `useSpeechToText` aborts its
recognizer and clears `useSTTStore`. The draft survives the call.

Errors reach the app as a `VoiceErrorCode` beside the SDK's English sentence,
and the app says them in its own language (`voice.errors.*`).

## Entitlements and billing

The app gates calls on the plan's `voice-mode` capability, as before. The
`voice-minutes` allowance is retired: it was an Alia-local count of LiveKit
session minutes in `voice_call_usage`, whose only writer left with the LiveKit
route, so it enforced nothing. Migration `0074_voice_minutes_retired` (post
phase) removes the feature rows and drops the table, and
`GET /billing/voice-usage` is gone. The same migration removes the
`voice-cohost` feature, a second realtime voice in the LiveKit room that the
on-device call does not have. Each voice turn and each spoken sentence is
billed per call by Oxy like any other chat or speech request
([ADR 0005](./adr/0005-product-entitlements-versus-financial-ledger.md)).
