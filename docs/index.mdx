# Alia

Alia is a multi-surface context-agent platform focused on autonomous execution with policy controls. One runtime powers the Expo app, the Codea VS Code extension, the Cowork desktop client, the developer CLI, and every webhook-driven trigger — all on top of a shared autonomy loop and a persistent context graph.

## What it is

A single chat runtime (`/alia/chat` and `/v1/chat/completions`) serves every surface. Each turn runs the autonomy loop `classify → recall → retrieve → act → learn`, draws from a per-user context graph, and is governed by an explicit risk policy (`R0`/`R1`/`R2`/`R3`) so writes are reversible, external impact requires approval, and destructive actions are blocked.

Model access goes through thirteen `alia-*` identifiers. Upstream routing is never leaked to clients, product errors or customer-facing analytics. Several of those identifiers are routing policies rather than models, and the set is frozen — [model abstraction](./model-abstraction.mdx) says which is which, and [ADR 0003](./adr/0003-model-revision-deployment-provider-routing-profile.md) records the vocabulary that replaces them.

```
     User  ────────────────>|   iOS, Android)   |

                                      |

                                      |
                            +---------v---------+
                            |  Express API      |
                            |  (packages/api)   |
                            +--+----------+-----+
                               |          |
              +----------------+          +-----------------+
              |                                             |
     +--------v---------+                       +-----------v-----------+
     |   PostgreSQL     |                       |  Upstream model       |
     |   (drizzle)      |                       |  endpoints, called    |
     +--------+---------+                       |  in process           |
              |                                 +-----------------------+
     +--------v---------+
     |  Redis (Valkey)  |     Socket.IO (real-time events,
     |  rate limits,    |     approval requests, streaming)

```

A MongoDB connection is still opened alongside PostgreSQL for the domains that have not been ported — conversations, messages, agents, organizations, containers, skills and a few more. It is not a readiness dependency. Under [ADR 0001](./adr/0001-alia-oxy-relay-responsibility-boundary.md) the in-process model calls move behind one typed client for a separate data plane (working name Relay), which does not exist yet.

## Install

The monorepo uses Bun workspaces and Turbo. Bun is the only supported package manager.

```sh
bun install
```

Copy `packages/api/.env.example` to `packages/api/.env` and fill it in. `DATABASE_URL` is the only variable the API cannot start without. `MONGODB_URI` is optional and covers the domains not yet ported; its database name is computed as `alia-{NODE_ENV}`, so do not embed it in the URI. Upstream model credentials are not environment variables — they live in the `provider_keys` table.

## Quick start

Boot the full stack:

```sh
bun run dev
```

Or run individual workspaces:

```sh
bun run dev:api          # Express API only
bun run dev:app          # Expo app (web + tunnel)
bun run dev:admin        # Admin console
bun run dev:canvas       # Canvas app
bun run dev:codea        # VS Code extension
bun run dev:cowork       # Electron desktop app
```

Hit the unified chat endpoint:

```ts
const res = await fetch('https://api.alia.onl/v1/chat/completions', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    Authorization: 'Bearer alia_sk_…',
  },
  body: JSON.stringify({
    model: 'alia-v1',
    messages: [{ role: 'user', content: 'Prepare my meeting with Sarah' }],
    stream: true,
  }),
});
// SSE stream — see "Chat runtime" for the event contract.
```

`alia_sk_*` credentials authenticate `api.alia.onl/v1/*` inside a bounded compatibility window. New integrations register in Oxy Console and call `api.oxy.so/v1` — see [developer access](./developers-portal.md).

## Core concepts

### Autonomy loop

Every chat turn runs the same five-step loop in `packages/api/src/lib/autonomy/runtime.ts`:

1. **classify** — detect intent (`meeting_prep`, `inbox_digest`, `project_status`, `task_followup`, `monitoring`, `research`, `general`)
2. **recall** — load ranked `ContextSource`s and `LearningRule`s from the per-user context graph
3. **retrieve** — pull data from top sources (integrations, MCP servers, Oxy ecosystem services)
4. **act** — produce the answer, call tools, stream the response over SSE
5. **learn** — update source quality scores and persist new `LearningRule`s

The loop is shared verbatim across app, Codea, and Cowork. Feature flags (`AUTONOMY_RUNTIME_ENABLED`, `AUTONOMY_CONTEXT_GRAPH_ENABLED`, `AUTONOMY_APPROVALS_ENABLED`, `AUTONOMY_ROLLBACK_ENABLED`, `AUTONOMY_OXY_EVENTS_ENABLED`) gate each stage and default to enabled.

### Context graph

Persistent autonomy state:

| Table | Tracks | Read through |
|-------|--------|--------------|
| `context_sources` | freshness, precision, average cost, latency, failure rate of a source | `db/autonomy/contextGraphRepository.ts` |
| `context_nodes` | entities discovered during retrieval (people, projects, docs, threads) | `db/autonomy/contextGraphRepository.ts` |
| `context_edges` | relationships and confidence weights between nodes | `db/autonomy/contextGraphRepository.ts` |
| `retrieval_strategies` | per-intent source ordering and fallback paths | `db/autonomy/contextGraphRepository.ts` |
| `learning_rules` | persisted corrections, constraints, and preferences | the Mongoose `LearningRule` model — not ported yet |
| `rollback_records` | before/after state and rollback payload for `R1` writes | the Mongoose `RollbackRecord` model — not ported yet |

User-visible memory (preferences, long-term facts, occupation, tone) lives in `user_memories` and `user_memory_entries`, exposed via `/memory/*`.

### Risk governance

Every action carries a risk class enforced by the runtime:

| Level | Meaning | Behavior |
|-------|---------|----------|
| `R0` | Read-only | Fully autonomous |
| `R1` | Reversible write | Autonomous + `RollbackRecord` saved |
| `R2` | External / unknown impact | Requires user approval over Socket.IO (`alia.approval_request` / `alia.approval_result`) |
| `R3` | Destructive | Blocked |

Approvals are real-time. The client receives `alia.approval_request` while the stream is paused and resolves it with an `approve` / `deny` decision; timeouts default to 60s.

### Model abstraction

The product surface exposes thirteen `alia-*` identifiers and nothing beneath them:

- In the picker: `alia-lite`, `alia-v1`, `alia-v1-pro`, `alia-v1-thinking`, `alia-v1-pro-max`
- Addressable but not in the picker: `alia-v1-codea`, `alia-v1-cowork`, `alia-v1-browser`, `alia-v1-vision`, `alia-v1-audio`, `alia-v1-multimodal`, `alia-v1-voice`, `alia-v1-voice-pro`

Each identifier carries a tier, and each tier maps to a ranked list of upstream deployments (`ModelMapping` in `packages/api/src/internal/providers/lib/alia-models.ts`). The fallback engine walks that list in `priority` order, skipping any entry whose circuit breaker is open. Errors pass through `sanitizeMessage()` (`packages/api/src/lib/errors/sanitize.ts`) before reaching a user-facing surface, which strips upstream names, model ids and endpoints.

Two of those identifiers share a tier, several are routing policies rather than models, and the whole set is frozen and inside a compatibility window. [Model abstraction](./model-abstraction.mdx) has the full table and the retirement gate.

### Trigger engine

The only scheduling primitive is `/triggers`. Trigger types:

- `schedule` — cron, daily, or interval
- `webhook` — token URL with optional HMAC and IP allowlist
- `integration_event` — matched by `service + event + filters`
- `agent_heartbeat` — periodic agent health / status check

Each run writes a `trigger_executions` row with status, tool calls, token usage and duration, through `db/automation/triggerRepository.ts`. Trigger actions follow the unified action contract: `{ prompt, agentId?, roleId?, useTools, notify?, channelId? }`.
