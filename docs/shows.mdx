# Shows

A show is a **podcast series on Syra** (`syra.fm`), Oxy's podcast product. Alia
owns the recipe and the job; Syra owns the published artifact.

That split decides almost everything else on this page. Alia stores what it
takes to produce an episode — the brief, the cast, the script's segments, the
progress and the credits — and stores **no audio**. There is deliberately no
`audio_url` column: the finished MP3 is handed to Syra and served from there,
under Syra's visibility rules and its own HLS transcode. A second address for
one recording would diverge the first time an owner made a show private.

## Everything is a series

A one-off show is a series with one episode. Syra requires it — `episodes.podcast_id`
is NOT NULL — and it means "give me another episode" needs no special case.

| Table | Holds |
|---|---|
| `show_series` | One row per Syra podcast: title, brief, format, cast, visibility, `syra_podcast_id`, `next_episode_number` |
| `show_episodes` | One row per episode: number, title, topic, status, segments, recap, `syra_episode_id`, the ingest ticket |
| `show_preferences` | An account's default visibility and format |

Voices are cast **once, when the series is created**, and every episode reads
`series.speakers`. A podcast whose hosts changed voice between episodes would be
absurd, and the per-episode assignment this replaced did exactly that.

## The brief belongs to the series, so an episode asks for nothing

**"New episode" is one press.** Nobody is asked what it should cover, because
the show already knows what it is about: `show_series.brief` is its standing
premise and the subjects earlier episodes used say what it has already spent.
The script model is handed both and chooses. `POST /shows/series/:id/episodes`
therefore accepts a request with **no body at all**.

An owner may still steer one. `topic` and `title` both survive as **optional
overrides — not rival defaults** — for the week when there is an election result
to cover, an article to work from, or a name already in mind. Each has the same
precedence: supplied, it is stored and nothing second-guesses it; absent, the
pipeline decides. What was removed is the requirement, not the ability.

That precedence is what makes both columns nullable. Storing a placeholder
instead would leave "the owner chose this name" and "nothing has named it yet"
looking identical, and the only way back would be guessing from whether a string
LOOKS generated.

### Two memories, at two different costs

| | Column | Sent | Costs |
|---|---|---|---|
| Breadth | `show_episodes.topic` | every earlier episode, one line each | ~15 words per episode |
| Detail | `show_episodes.recap` | the last three | a paragraph each |

Recaps alone are exactly how a show repeats itself at episode nine: the window
holds 6, 7 and 8, and episode 2 is as invisible to the model as if it had never
aired. So `topic` became the series' long memory — one line per episode is
affordable for fifty of them, and it is what the prompt lists under *"these
subjects are used up"*.

`priorEpisodes()` reads both in one query and excludes only **failed** runs. A
run that died said nothing to a listener, so holding its subject back would
retire a subject the show never actually did; an episode still *recording* is
kept, because it has already claimed one — that is what stops two episodes
queued a minute apart covering the same thing.

**Two honest limits.** The ledger keeps the newest fifty, so a show longer than
that may revisit something from beyond it. And three episodes whose scripts are
being written in the same moment still see the same list: the subject is written
the instant the script parses, which shrinks that window from the whole run to
one model call, but does not close it.

**A thin brief is the real failure mode.** Ten characters is a valid brief and
gives a show with nothing to vary along — the ledger will stop it repeating
itself literally and cannot make it about anything. The series dialog says so
where an owner will read it; the schema cannot.

## Routes are `/shows`, not `/v1/shows`

`/v1` is a frozen compatibility surface that gains no route (ADR 0004), and the
workstream 1 inventory assigned shows to Alia product. So they sit at `/shows`,
beside `/conversations`, `/skills`, `/agents` and `/library`.

```
POST|GET    /shows/series
GET|PATCH|DELETE /shows/series/:id
POST        /shows/series/:id/episodes
GET|DELETE  /shows/episodes/:id
GET         /shows/voices
GET|PUT     /shows/preferences
```

## Deleting removes Alia's record only, and that is a LIMIT, not a preference

Deleting either a series or an episode removes **Alia's record only**. The
podcast is published and may have listeners, which is a reason to be careful —
but it is not why it works this way. **Syra exposes no delete for a podcast or
an episode.** Measured against `packages/backend/src/routes/podcasts.routes.ts`
and `episodes.routes.ts`: the mutations are `POST /:id/publish`,
`POST /:id/unpublish` and `PATCH /:id`, and there is no `router.delete` on
either router. Syra's own studio offers neither control, and `@syra.fm/sdk`
exposes neither endpoint. So a person who removes a show here still owns a
podcast there, and no code in this repository can change that.

Two consequences worth stating, because both are reachable today:

- **Unpublish is not a stand-in, for the owner least of all.** `status:
  'unavailable'` hides a show from a stranger — browse, search, `GET
  /api/podcasts/:id` and its RSS feed all 404 through `findPodcastForViewer`.
  It does not hide it from its OWNER: `GET /api/podcasts/mine` filters on
  nothing, so an unpublished show stays in the creator's own library, which is
  precisely where the person who pressed delete goes looking. Nor does it stop
  playback — the media gate (`requestMayReachShowMedia`) reads the show's
  `visibility`, not its `status`, so a `public` or `unlisted` show's episodes
  keep serving from `/audio` after the show is unpublished.
- **Deleting a series mid-run does not stop the run.** `show_episodes.series_id`
  is `ON DELETE CASCADE`, so the episode rows and their ingest tickets go with
  it, while a job already past `findEpisodeById` keeps its local copy and
  publishes the finished audio to a podcast Alia has forgotten.

Until Syra offers a delete, the UI's job is to not overstate what its button
does: the control says **"Remove from Alia"**, a confirmation says the podcast
stays published on Syra BEFORE the press, and the success message is sent only
after the request actually succeeded.

## The ingest ticket, and why it cannot be a service token

**This is the part most likely to be "simplified" by somebody who has not read
this paragraph.**

Syra authenticates exactly one thing: a user's Oxy JWT. Alia's show pipeline runs
in a BullMQ worker minutes after the request, and by then it holds no user
credential. Service-token delegation is closed platform-wide until ADR 0012's
Ed25519/JWKS migration lands and every verifier ships a JWKS-capable core.

So the two halves are split deliberately:

- `POST /shows/series/:id/episodes` runs while the caller's token is live. It
  reserves the Syra episode (`createEpisodeDraft`) and stores the **single-use
  ingest ticket** Syra answers with.
- The worker redeems that ticket (`ingestEpisode`), authenticated by the ticket
  alone, and clears it.

A service credential in place of the ticket would simply be refused, and there is
no shortcut past it. `lib/syra/syra.ts` is the whole seam: two clients, one
carrying the caller's token, one carrying nothing. Every call goes through
`@syra.fm/sdk` — Syra owns its wire format the way Kaana owns inference.

### The name is written twice, and the second one is real

Syra requires a `title` to reserve the draft, minutes before any script exists.
So the route sends a **placeholder** — `Episode {n}`, the one thing that is
certainly true — and the pipeline replaces it once the script is written, from
what the episode actually says. The placeholder goes to **Syra only**; the Alia
row stays `null`, because that null is what says nobody has named this yet.

An owner who did name it wins on both sides at once: the draft is reserved under
their name, the row stores it, and the pipeline finds a title already there and
leaves it alone. Precedence in one line — **owner, then script, then
`Episode {n}`.**

It used to have to be decided in the route, from the topic, because Syra's
ingest allowlist refused a title outright: a capability has no business renaming
a published episode. That name was a name for an episode nobody had written yet,
and production shows what it produced — see the census in migration `0040`.

The ingest sends the name **unconditionally**, including when the owner chose
it — that is the same string the draft was reserved under, so it is a no-op
there and one code path here rather than two. Syra reads an *absent* title as
"keep the draft's", never as "blank it", which is precisely why omitting it on
the fallback path would look correct and be wrong everywhere else.

Two details that are not incidental:

- **`title` is the LAST field in the script's JSON schema**, after `segments`. A
  model fills an object in the order it is given, so a title asked for above the
  dialogue is a title written from the subject — the very thing this replaced.
  `recap` sits there too, for the same reason.
- **A bad reply falls back to `Episode {n}`.** `cleanTitle()` answers `null` for
  an explanation, a list of candidates or a paragraph. That is the same string
  the draft was reserved under, so the fallback changes nothing on either side.
  Refusing to publish an episode over its name would be absurd.

There is still no route to RENAME an episode after it exists — a rename is
Syra's to accept, with the owner's own token, and that call does not exist here.
Naming one up front does.

## Playback is `/audio`, not `/stream`

A series defaults to **private**, and Syra does not transcode a private show —
its own words, at `services/podcasts/ingestEpisode.ts`: *"a private show's
episodes stay on the progressive `/audio` path, which is checked per request
against the show's current visibility."*

So `GET /api/podcasts/episodes/:id/stream` answers `409` or `422` for exactly the
episode a user just made. `GET /api/podcasts/episodes/:id/audio` with the
listener's bearer token works at every visibility, needs no hls.js on the web,
and is the enclosure Syra publishes in its own RSS. Syra gates it on the SHOW's
audience and never on who is asking — `public` and `unlisted` are anonymous
because podcast clients fetch that same URL with no credentials, and only
`private` asks, answering anyone but the owner `404`.

**Web has to fetch the audio itself, and that is not optional.** `expo-audio`
takes `{ uri, headers }` and sends the headers on native only: in `57.0.0` the
sole web function that reads `source.headers` is `preloadAsync`, and
`AudioPlayer.web`'s `_createMediaElement` hands `new Audio()` the raw URI unless
`preloadCache` already holds a blob for it. Nothing called `preloadAsync`, so a
browser asked Syra for a private episode anonymously, got `404`, and reported
`NotSupportedError: Failed to load because no supported source was found` — a
message that names the symptom and hides the cause, and one that only ever
appeared on web. `lib/hooks/use-episode-audio.ts` owns the fetch on web now:
it checks the STATUS before treating the body as audio (`preloadAsync` calls
`response.blob()` with no `ok` check, which is how a refusal became undecodable
audio), plays from an object URL revoked at the end of that one playback, and
gives each refusal — signed out, rejected token, nothing there, unreachable —
its own sentence in the episode row.

**Syra never computes an episode's duration** — the draft inserts `0` and only
the ingest field sets it. Alia measures the finished file with ffmpeg rather than
estimating from its byte length, because the figure it sends is permanent: a
wrong one shows in Syra's episode list and in the feed forever.

## Cover art

Generated when the series is created, uploaded to Syra, and **never allowed to
block creation**. Every failure answers "no image": Syra's own surfaces already
handle a show without artwork, and a series nobody could create because an image
model was busy would be the worse outcome. `PATCH /shows/series/:id` replaces it.

## Sound effects

The script asks for an intro, transitions between topics and an outro, and each
one is an `sfx` segment carrying an `sfxPrompt`. They are rendered by
`lib/synthesize-sound-effect.ts`, which walks the **`v1-sfx` tier** and takes the
first provider that answers — the same shape `synthesize-speech.ts` has for the
`v1-tts` tier, and for the same reason: a chain with one entry is exhausted on
its first attempt.

It had one entry, inline, and no chain. `renderSoundEffect` named a single
provider and a single model in the pipeline, so when that provider held no
credential every sound cue in every episode was lost — permanently, three per
episode, while the episode published and reported success. Adding a provider to
the tier is a `createMapping` line; adding one to a hardcoded call was a
rewrite, which is why the failure survived as long as it did.

**How deep that chain is, honestly.** Three mappings across two providers, and
in production today exactly one of those providers holds a credential:
ElevenLabs. The `fal` entry is refused before a request leaves the process, so
against the failure that actually happened — a provider with no key — the
effective depth is one until an operator installs a DigitalOcean key. The second
ElevenLabs mapping covers a MODEL fault and shares the first one's credential,
so it covers no key fault. The tier's own comment in
`generate-model-mappings.ts` says which entry covers what, and why there is no
fourth without a provider integration, which belongs to Kaana rather than here.

**Dialogue is rendered before effects, deliberately.** Speech is the part a
listener cannot do without, and an effect provider timing out used to poison the
key pool before the voices had finished.

**A cue that cannot be produced is recorded, not swallowed.** The pipeline still
publishes — a missing transition whoosh is a slightly abrupt show, and refusing
over it is no show — but the segment is marked `renderFailed`, so the row says
which cues are missing and what they were meant to sound like, and the series
screen says so too. The same applies to a spoken line. An episode that quietly
loses everything it asked for is worse than one that admits it.

## Configuration

| Variable | Where | Notes |
|---|---|---|
| `SYRA_API_URL` | API | Defaults to `https://api.syra.fm`. No secret — Syra authenticates the caller, not the service. |
| `EXPO_PUBLIC_SYRA_API_URL` | App | Deliberately not tied to the API URL: a local API still plays episodes from the real Syra. |

**One prerequisite lives in Syra, not here.** Web playback fetches audio from
`api.syra.fm` with the listener's token, and `Authorization` is not a
CORS-safelisted header, so the request is preflighted and Alia's web origin must
be listed EXACTLY in Syra's `ALLOWED_ORIGINS` (`packages/backend/server.ts`).
`https://alia.onl` is listed. No local origin is: neither
`http://localhost:8150` (`bun run --filter @alia/app web`) nor the random
`*.exp.direct` host `dev:app`'s tunnel hands out, which could not be listed
anyway. Syra's origin callback answers `false` rather than an error, so the
preflight simply comes back without `Access-Control-Allow-Origin` and the fetch
rejects. A developer playing an
episode from a local web build therefore reads *"Couldn't reach Syra"*, which is
the truth: the request never got an answer. Nothing in Alia can fix that from
here; it is one line in Syra, and only worth adding if local web playback is
something we want to be able to try. Native sends no `Origin` at all and is
unaffected either way.

Key files: `db/schema/shows.ts`, `db/shows/showRepository.ts` (`priorEpisodes`),
`lib/show/` (pipeline, prompts, voices, audio, cover art, titles),
`lib/syra/syra.ts`, `routes/shows.ts`.
