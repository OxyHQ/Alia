# Integrations and tools

Alia's reach across channels and external systems comes from three layers:

1. **Native tools** registered in `packages/api/src/lib/tools/` — the runtime exposes them to the model directly.
2. **MCP servers** — Model Context Protocol bridges to user-installed tools.
3. **Channel integrations** — long-running connectors in `packages/integrations/` that mirror messages from Telegram, WhatsApp, Discord, Signal, Gmail, and a headless browser into Alia.

## Native tools

Tools live in `packages/api/src/lib/tools/` and self-register through `registry.ts`. Each tool declares its name, description, default-enabled state, and category; the runtime assembles the per-request tool set based on the user's plan, the model's capabilities, and any explicit `tools` list on the request.

| Category | Tools |
|----------|-------|
| Utility | `getCurrentDate`, `getDeviceInfo`, `switchModel` |
| Research | `webSearch`, `webScraper`, `browse`, `deepResearch` |
| Memory | `saveUserMemory`, `updateUserPreferences`, `updateUserContext` |
| Generation | `generateFile`, `canvas` |
| Agents | `searchAgents`, `delegateToAgent`, `orchestrateAgents`, `createAgent`, `delegateSubtask` |
| Triggers | `createTrigger`, `listTriggers`, `updateTrigger`, `deleteTrigger` |
| Channels | `sendTelegramMessage`, `sendWhatsAppMessage`, `getWhatsAppChats`, `getWhatsAppMessages` |
| Infrastructure | `sandbox`, `gatewayAdmin`, `planPreview` |
| Bridges | `mcp`, `oxy-services`, `integrations` |

All tools wrap their executor in `safeExecute()` so errors surface as `alia.tool_result` events without breaking the SSE stream. Risk class is declared per-tool and enforced by the autonomy runtime — `R2` calls pause the stream for approval, `R3` calls are blocked outright.

### Adding a tool

1. Create `packages/api/src/lib/tools/my-tool.ts` exporting a tool constructor
2. Export it from `packages/api/src/lib/tools/index.ts`
3. Register it with `registerTool({ name, description, tool, enabledByDefault, category })`
4. Pick a risk class and wrap any external write in a `RollbackRecord` if reversible
5. Add a description fragment under `packages/api/src/lib/tools/descriptions/`
6. Test it under `packages/api/src/lib/tools/__tests__/`

## MCP servers

MCP integration lives in `packages/api/src/lib/tools/mcp.ts` and `packages/integrations/src/mcp/`. Users register MCP servers from their account; tools are introspected via `mcp-schema.ts` and surfaced as first-class tool calls inside chat. The runtime handles transport (stdio / HTTP / websocket), schema validation, lifecycle, and rate limiting per server.

MCP capabilities are visible to the model with the same calling convention as native tools, so the LLM does not need to distinguish them. Per-user MCP policy is exposed through `GET /codea/mcp_registry` for the Codea VS Code surface.

## Oxy service connector

Alia is part of the Oxy ecosystem. Each app registers one signed capability
catalog in Oxy; Alia builds its internal tools from that registry. Adding an app
requires a catalog and handlers in the app, not app-specific code in Alia.

- Oxy owns catalog registration, delegations and live authorization decisions.
- `packages/api/src/lib/tools/oxy-services.ts` turns internal catalog tools into AI SDK tools.
- `packages/api/src/lib/oxy-capability-authority.ts` exchanges request-scoped user approval for opaque execution-authorization ids.

Inbound service events go through `POST /webhooks/oxy`:

- The Oxy service bearer is verified centrally; Alia stores no per-app HMAC secret.
- The publisher may emit only events declared by a catalog it owns.
- `(appId, eventId)` is deduplicated before matching automations.
- Observation records actor/action decisions with no execution.
- Execution requires every declared resource/tool authorization, then obtains a
  short-lived capability ticket for the fresh run and step.

User sessions are never forwarded to apps or retained by background runs. The
app receives only a one-minute capability ticket with its exact audience,
resource, actor, account, run, step and tool.

## Channel integrations

`packages/integrations` is a separate Express service that owns long-lived connections to messaging platforms. It mirrors channel messages into Alia conversations and exposes outbound tools the runtime can call.

| Subdirectory | Channel | Notes |
|--------------|---------|-------|
| `accounts/telegram-gateway/` | Telegram user accounts | MTProto bridge |
| `accounts/whatsapp/` | WhatsApp Web | Multi-device bridge with chat / message sync |
| `accounts/signal/` | Signal | Bridge for Signal accounts |
| `accounts/gmail/` | Gmail | IMAP / Gmail API sync |
| `bots/telegram-bot/` | Telegram bot | Bot API bridge |
| `bots/discord-bot/` | Discord | Bot user that mirrors guild channels |
| `browser/` | Headless browser | Used by `browse` and `webScraper` tools |
| `terminal/` | Terminal sessions | Used by Codea CLI for shell access |
| `realtime/` | Realtime audio | Voice-tier model bridge |

Inbound messages arrive at the API as either:

- **Channel-bound conversations** — each chat becomes a conversation scoped to that channel and a user, so the autonomy loop can reuse the same context graph
- **Webhook events** — for trigger-driven actions, the integration emits an `integration_event` matched by `service + event + filters`

Outbound tools (e.g. `sendTelegramMessage`, `sendWhatsAppMessage`) require `R2` approval by default. The trigger engine respects the same risk class when integrations call tools autonomously.

## Triggers

`/triggers` is the transitional scheduler. `/automations` is the normalized
control plane that stores the objective, actor selection, trigger, exact actions,
data flow, limits, autonomy and `observe | execute` mode. It does not create a
second scheduling loop.

```ts
type TriggerType = 'schedule' | 'webhook' | 'integration_event' | 'agent_heartbeat';

interface TriggerAction {
  prompt: string;
  agentId?: ObjectId;
  roleId?: string;
  useTools: boolean;
  notify?: boolean;
  channelId?: string;
}
```

Each invocation runs the same autonomy loop as a chat turn, writes a `TriggerExecution` record (status, tool calls, token usage, duration), and respects the user's risk policy. Webhook triggers expose a token URL with optional HMAC and IP allowlist; integration triggers match against the event filter; heartbeats run on a fixed cadence.

Endpoints:

| Method | Path | Purpose |
|--------|------|---------|
| `GET` | `/triggers` | List user triggers |
| `POST` | `/triggers` | Create trigger |
| `PATCH` | `/triggers/:id` | Update trigger |
| `DELETE` | `/triggers/:id` | Delete trigger |
| `POST` | `/triggers/:id/run` | Manual run |
| `GET` | `/triggers/:id/executions` | Execution history |
| `POST` | `/triggers/webhook/:token` | Public webhook entry point |

Structured control-plane endpoints:

| Method | Path | Purpose |
|--------|------|---------|
| `GET` | `/automations` | List definitions and declared actions |
| `POST` | `/automations` | Create an observe/execute definition and editable receipt |
| `PATCH` | `/automations/:id` | Enable or stop; reauthorization is required after a stop |
| `DELETE` | `/automations/:id` | Stop immediately and revoke its Oxy authorizations |
| `GET` | `/automations/runs` | Decision and execution history |
| `GET` | `/automations/runs/:runId/steps` | Ordered, correlated step history |

## Sandbox and Docker host

`packages/alia-docker-host` provides per-conversation isolated containers for code execution and ephemeral environments. The `sandbox` tool spawns containers from `ContainerTemplate` definitions and the runtime garbage-collects idle containers after the chat closes. Use the Docker host for any tool that needs filesystem isolation, shell access, or network egress controls.
