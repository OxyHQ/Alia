# Kaana routing-profile cleanup

Alia no longer presents an Alia-branded provider alias as a model. Product
surfaces request one of two explicit identities:

- a Kaana routing profile such as `kaana-v1`; or
- a concrete `<publisher>/<model>[@<revision>]` reference.

The active TypeScript vocabulary is `RoutingProfile`,
`KAANA_ROUTING_PROFILES` and `routingProfileId`. PostgreSQL stores the same
concept as `routing_profiles.routing_profile_id`; cost, fallback, voice and chat
analytics use `routing_profile_id` or `routing_profile`. Migrations 0055 and
0056 perform the rolling rename and remove their temporary compatibility
surface after the new image is stable. Applied migrations before 0055 retain
their original text because they are immutable upgrade history.

## Ownership boundary

Alia owns product policy: which profile a surface asks for, entitlements,
prompts, tools and the customer-facing result. It does not own provider
credentials, provider adapters, deployment selection or provider fallback.
Those belong to Kaana. Upstream provider credentials live encrypted in Kaana's
database and are never delivered to Alia through environment variables.

The local provider catalogue under `packages/api/src/internal/providers/` is a
transitional extraction source, not a hosted inference path. Architecture gates
refuse direct hosted-provider egress; user-owned runtimes remain a separate,
explicit product path and do not use Kaana's credential pool.

## Current serving blocker

The direct Alia transport signs and posts an `InferenceRequest` to Kaana. Alia
cannot authorize a routing profile by itself: Oxy resolves customer policy and
adds the ordered, signed `authorizedRoutes` list. Kaana intentionally refuses a
routing-profile target without that list.

Therefore the hosted cutover is not complete until Alia enters through Oxy's
inference edge, or another reviewed Oxy-owned boundary supplies the exact
authorized routes before signing. No default region, provider, deployment or
empty-list fallback may be invented in Alia.

## Removal gates

The cleanup is complete only when all of these remain true:

1. Active source and schemas contain no former Alia-provider alias identifiers.
2. Alia runtime tasks contain no upstream-provider credential variables.
3. Provider credentials are readable only by Kaana's credential roles and are
   absent from Alia's database after the production data-removal migration.
4. Every hosted routing-profile request crosses Oxy policy resolution and
   reaches Kaana with non-empty, signed `authorizedRoutes`.
5. Kaana canaries prove the selected route, usage receipt and customer
   attribution before the previous serving path is retired.
