# Kaana model abstraction

Alia is a product consumer of Kaana through Oxy. Alia owns product modes,
prompts, conversation state and user-facing presentation. Oxy authenticates,
authorizes and orders the exact deployment routes. Kaana owns provider
credentials, deployment execution, health, retries, failover within that signed
order and technical usage against the upstream execution plane.

There is no hosted direct-provider mode in Alia. Provider environment keys and
`GATEWAY_API_URL` are refused at boot rather than treated as alternate
configuration.

## Product vocabulary

The public vocabulary deliberately separates three things:

- A **product mode** is what a person selects in Alia, such as Automatic, Fast,
  Balanced, Maximum quality, Coding or Deep research. Modes are serialized as
  `object: "product_mode"`.
- A **product routing profile** is a canonical `kaana-*` identifier at Alia's
  public boundary. It is configuration with no weights, is matched only by
  exact ID and is never serialized as a concrete model. Alia's reviewed closed
  map translates it to an opaque Oxy profile primary key; Oxy validates that
  exact row before the Kaana v2 envelope. Neither Oxy nor Kaana looks up the
  product spelling.
- A **model reference** uses canonical `<publisher>/<model>` form. An immutable
  revision adds `@<revision>`. A concrete reference remains concrete through the
  request path.

The canonical routing-profile set is defined in
`packages/api/src/lib/routing/kaana-profiles.ts`. Product visibility belongs to
`packages/api/src/lib/product-modes.ts`; changing what Alia offers does not
change Kaana's provider routing. The subset provisioned in Oxy and its exact
opaque IDs are pinned in
`packages/api/src/config/oxy-inference-routing-profile-ids.ts`; an absent entry
fails closed.

## Hosted request path

For hosted text inference:

1. The request boundary validates the requested product mode or Kaana profile.
2. `packages/api/src/lib/chat-core.ts` produces a credential-free resolution
   carrying an explicit `routing_profile_id` or `model` target.
3. `getAIModel()` returns the Kaana AI SDK adapter.
4. `@oxyhq/core`'s `OxyInferenceClient` authenticates to Oxy with Alia's
   short-lived service credential.
5. Oxy resolves identity and authorised routing policy, then signs and forwards
   the request to Kaana. Kaana owns every provider-side execution decision.

Alia performs one hosted attempt. It does not rotate provider keys, construct
provider clients or widen a policy after an error. Provider health and
credentials stored for migration cannot influence this request path.

The one explicit exception is a user's connected local runtime. That path uses
the user's own runtime binding and intercepted fetch bridge; it never becomes a
hosted fallback and never uses a provider environment key.

## Capabilities

Text chat uses the Kaana seam. Hosted image generation, speech synthesis, audio
generation, transcription, voice sessions and embeddings do not yet have a
Kaana capability seam in this repository. Those routes fail closed with HTTP
503 and `KAANA_CAPABILITY_UNAVAILABLE` before provider selection, billing or
egress.

A new hosted modality is complete only when its typed Kaana/Oxy contract and
transport exist. Reconnecting an old provider adapter is not an implementation
of that capability.

## Catalogue surfaces

`GET /catalogue` is the product catalogue. It distinguishes product modes,
routing profiles and concrete model references by type; clients do not infer
meaning from identifier spelling.

`GET /v1/models` remains the bounded OpenAI-compatible surface documented by
ADR 0004. It must not misrepresent a routing profile as a concrete model.

## Credentials and retained migration data

Provider credentials belong to Kaana's database. Alia does not read provider
API keys from its environment and cannot enable hosted inference with one.

The routing catalogue and its foreign keys use `routing_profiles` and
`routing_profile_id`; older names survive only inside immutable migration history.
The post-rollout migration
`packages/api/drizzle/0061_remove_alia_provider_credentials.sql` drops Alia's
legacy `provider_keys` table without reading or copying its contents. Current
source contains no hosted credential reader. Historical health, usage and
fallback tables remain non-runtime migration evidence; their presence does not
restore a direct-provider path. Applying the destructive migration in
production still requires the exact deployed-migration readback in the
[Kaana cutover runbook](./runbooks/kaana-cutover.md).

Alia contains no hosted provider adapter tree or administrative provider-key script.
Product inference cannot import or construct a direct provider client.

## Errors and observability

Product errors expose Kaana profile vocabulary, never an upstream operator,
credential or endpoint. `sanitizeMessage()` remains the product-surface guard,
while logs and migration tooling may retain the exact historical identity they
need to reconcile data.

The runtime boundary is enforced by architecture tests that require the
published Oxy SDK, reject retired signing/transport files and forbid provider
or direct-Kaana configuration. The boot guard also refuses provider-host egress
before a socket opens. The local user-runtime exception remains explicit and
can never become a hosted fallback.
