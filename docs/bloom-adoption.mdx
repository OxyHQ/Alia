# Bloom adoption

## Current app composition (September 2026)

The Expo app declares Bloom `^4.5.0` and composes Bloom's AI Chat template
(`templates/ai-chat/AiChatTemplate.tsx` in Bloom) **literally**: the same
components, in the same order, with the same props. The router still owns URLs
and conversation identity; app state, streaming, pagination, authentication,
voice, tools and inference stay in Alia. The one surface of Alia's own is the
signed-out welcome (`welcome-intro.tsx` over `ambient-field.tsx`).

| Template | Alia |
| --- | --- |
| `<View style={TEMPLATE_FRAME}>` → `AiChatShell` | `app/(app)/_layout.tsx` |
| `sidebar={<Sidebar …/>}`, `mobileSidebar={<Sidebar … mobile surface="plain"/>}` | `components/sidebar.tsx`: `logo`, `items`, `secondaryItems`, `account`, `tree`, `plan`; the drawer copy inside `NavRegion` (#532) |
| `panel` (always, from `xl`) with `AiChatCodePanel` / `AiChatGalleryPanel` | `components/workspace-panel.tsx`: the canvas as the code panel, Library and generated images as the gallery; thought, credits and agent take the slot while open |
| `AiChatContainer project title header={<AiChatMobileHeader/>} working composer` | `components/chat-page-content.tsx` through `ChatWorkspace` (the native keyboard authority) |
| the pill + `ComposerStatusBar` | **`ComposerPanel`** instead (`components/chat/composer/composer.tsx`): provider-rail model picker with effort (`model-lineup.ts`), Chat / Agent / Deep research as its mode selector, attachment tiles, `ComposerPanelStatusTab` with the chat's project; the add menu in two groups (`add-menu.tsx`) |
| `AiChatThread` → `AiChatUserMessage` / `AiChatAssistantMessage` (feedback row) | `components/chat-interface.tsx` |
| `AiChatMessageLine`, `AiChatBulletList`, `AiChatStrong`, `AiChatLinkChip`, `CodeBlock` | `components/chat/bloom-markdown.tsx` renders each reply's Markdown into them |
| `AgentProgress` while working, then "Worked for …" (`tone="secondary"`) | the turn's tool calls, as the runtime reports them |

What the template has no room for was removed, not wrapped; the list, and the
Bloom slot each item comes back through, is
[`bloom-template-pending.mdx`](./bloom-template-pending.mdx).

### Validation and limits

Compared against the template running in Bloom's own Storybook (origin/main,
4.5.0) with Alia's `purple` preset, in a real browser, by measuring every
`data-bloom-*` box on both pages rather than by eye: 1440×900, 1280, 1100 (panel
as a drawer), 1023 (sidebar as a push drawer, open and closed) and 390×844, light
and dark, plus the collapsed rail. The composer pill, the shell frame and the
drawer land on the same pixels at every width; the remaining deltas are content
(the template's code panel, its project crumb, its scripted turn in flight). The
thread was checked through a temporary route rendering fixed messages, idle and
working; it is not shipped. No authenticated session, message send or inference
was exercised. TypeScript passes; the app suite passes (94 files, 731 tests); the
visual baseline was re-recorded and `--check` reproduces it (worst Δ3, ±6).

## 3. Verified contract gaps

Each gap was re-checked against 3.2.1. Two of the issue's claims turned out to be
imprecise; that is noted where it applies.

### 1. No `onStop` on either composer — CONFIRMED

`ComposerPillProps` and `ComposerPanelProps` both end at `onSubmit` plus a
`disabled` flag:

```ts
/** Fires on the send button and on Enter. */
onSubmit?: (value: string) => void;
/** Greys out send (40%) while a turn is in flight. */
disabled?: boolean;
```

A repo-wide grep of `src/**/types.ts` finds `onStop` in exactly two places, both
in `agent-chat`:

```ts
// agent-chat/types.ts — AgentChatComposerProps
onStop?: () => void;
/** Shows the stop disc and lights the `ComposerLoader` band. */
busy?: boolean;
```

So Bloom already knows the shape; it lives on the family Alia cannot adopt (see
the `agent-chat` row). Alia's `components/ui/prompt-input/submit-button.tsx`
swaps the send arrow for a `Square` labelled "Stop generating", with an explicit
`disabled={false}` so the stream-wide lock cannot reach it. With the pill as
shipped, `disabled` greys out the only action button while a turn runs — the
cancel affordance disappears exactly when it is needed. Overlaying a second
button at an arbitrary offset is what issue §2 forbids.

### 2. Model identity — CONFIRMED, and the issue's framing needs one correction

`ComposerPillProps` takes names:

```ts
/** Model names for the model menu. Omit to hide the model button. */
models?: ReadonlyArray<string>;
/** Controlled model name. */
model?: string;
onModelChange?: (model: string) => void;
```

`ComposerPillBase.tsx` confirms the behaviour — it maps over the strings and
compares by equality (`selected={name === model}`), and falls back to
`models?.[0] ?? ''`. Both the ambiguous display-name key and the first-item
fallback that issue §2 warns about are real.

`ModelPickerProps`, in the same family, does not have the problem:

```ts
export interface ModelPickerModel { id: string; name: string; }
export interface ModelPickerProps {
  providers: ReadonlyArray<ModelPickerProvider>;
  value?: string;            // model id
  onValueChange?: (modelId: string) => void;
}
```

`ComposerPanelProps` forwards that same `providers` / `model` / `onModelChange`
triple, and its `onModelChange?: (modelId: string) => void` is documented
"Controlled model id; see `ModelPicker`".

**So the identity problem is `ComposerPill`'s alone.** `ComposerPanel` and
`ModelPicker` are already correct. Alia's `components/model-selector.tsx`
already selects by opaque id (`onModelChange(model.id)`), matching the
[chat runtime](./chat-runtime.mdx) rule that a routing identifier is matched by
exact string equality and never by display name. Adopting the pill as shipped
would regress that; adopting `ModelPicker` beside it would not.

Effort is a separate axis in both: `effort?: number` indexing
`MODEL_PICKER_EFFORT_LEVELS` (`Low, Medium, Balanced, High, Very High, Max`,
default index 1).

### 3. `AiChatThread` has no timeline contract — CONFIRMED

The whole type:

```ts
export interface AiChatThreadProps {
  /** The turns. The thread follows the newest one with a smooth scroll as it grows. */
  children: ReactNode;
  style?: StyleProp<ViewStyle>;
  testID?: string;
}
```

The implementation is a plain `ScrollView` whose `scrollRef` is a module-private
`useRef`, with one behaviour — `onContentSizeChange` calls
`scrollToEnd({ animated: true })` whenever the content grows. There is no ref
forwarding, no `onScroll`, no `maintainVisibleContentPosition`, no
`onEndReached`, no virtualization.

What Alia would lose by swapping: `lib/hooks/use-scroll-to-bottom.ts` follows the
bottom **only while the reader is within 50px of it**, paginates history upward
when `contentOffset.y <= 300`, and re-applies an absolute scroll anchor on every
history layout so that loading older messages does not move the reader. Every
programmatic scroll there is `animated: false` by design.
`components/chat-interface.tsx` adds cursor jump via
`onRowLayout` on the row whose `cursor === focusCursor`. Bloom's unconditional
animated `scrollToEnd` would fight all four.

Bloom does ship the missing machinery — `VirtualList` has `onEndReached`,
`maintainVisibleContentPosition` and a `VirtualListHandle` with
`scrollToOffset` / `scrollTo` — it is simply not wired into `AiChatThread`, and
`VirtualListHandle` still has no `scrollToIndex`, so cursor jump has no
primitive either.

### 4. `AiChatContainerProps.project` is required — CONFIRMED

```ts
export interface AiChatContainerProps {
  /** The project crumb, after its folder glyph. */
  project: string;
  /** The current chat crumb. */
  title: string;
```

Both crumbs are unconditionally rendered as `BreadcrumbItem`s. There is no
`hideBreadcrumb`, no `ReactNode` override, and no union that lets `project` be
absent. Most Alia chats have no project. Passing `''` renders an empty crumb and
its folder glyph — a visible empty control, which issue §6 rules out. The
`header` slot renders *above* the breadcrumb, so using it for Alia's own header
stacks two headers rather than replacing one.

### 5. `ComposerAttachments` simulates uploads — CONFIRMED

`src/composer-panel/use-attachment-queue.ts` drives the ring itself:

```ts
const TICK_MS = 50;
const step = 100 / Math.max(1, uploadDuration / TICK_MS);
const tick = () => {
  // Uneven steps so the ring reads as a transfer rather than a timer.
  value = Math.min(100, value + step * (0.55 + Math.random() * 0.9));
```

and the hook's own doc comment says so:

> The upload is SIMULATED, so the block stays backend-agnostic; real uploads feed
> their own `progress` to `ComposerPanel` instead.

Concretely: an attachment handed to `ComposerAttachments` with `progress: 0` gets
a ring that fills over `uploadDuration` (default 1100ms) after a `uploadGap`
pause (default 240ms) from a `Math.random()` ramp, then `onUploadComplete` fires
**regardless of whether any byte moved**. There is no error state, no retry, no
cancel. Alia must use `ComposerPanel` with its own `attachments` array and set
each tile's `progress` from real upload events — and `ComposerPanelAttachment`
has no failure field, so a failed upload has no representation in the type at
all.

### 6. `AiChatFeedbackRow` announces success unconditionally — CONFIRMED

The type:

```ts
/**
 * Copy handler. The glyph swaps to a check and the tooltip reads "Copied!" for
 * 1.6s either way.
 */
onCopy?: () => void;
```

and `src/ai-chat/AiChatFeedbackRowBase.tsx` implements exactly that:

```ts
const copy = () => {
  if (timer.current) clearTimeout(timer.current);
  onCopy?.();
  setCopied(true);
  setCopyTooltipOpen(true);
```

The return value is discarded — the signature is `() => void`, so a promise
cannot even be awaited — and `setCopied(true)` runs unconditionally. A clipboard
permission denial shows "Copied!".

This is a defect specific to this row, not a Bloom convention. Two sibling
contracts get it right:

- `CodeBlockProps.onCopy: (code: string) => void | Promise<void>`
- `AgentChatMessageProps.onCopy: (text: string) => void | Promise<void>` —
  "Resolve (or return) to show the ✓ for 1.6s; throw to leave the icon unchanged."

Widening `AiChatFeedbackRowProps.onCopy` to match either is the fix.

### 7. Code and gallery panel defaults — CONFIRMED

Both panels default to action arrays whose entries carry **no `onPress`**
(`AiChatPanelAction.onPress` is optional):

```ts
export const DEFAULT_CODE_PANEL_ACTIONS: ReadonlyArray<AiChatPanelAction> = [
  { key: 'terminal', label: 'Open terminal', icon: RiTerminalFill },
  { key: 'expand', label: 'Expand panel', icon: RiExpandDiagonalSLine },
  { key: 'toggle', label: 'Toggle panel', icon: RiSideBarLine },
];
export const DEFAULT_GALLERY_PANEL_ACTIONS: ReadonlyArray<AiChatPanelAction> = [
  { key: 'new', label: 'New generation', icon: RiImageAddLine },
  ...
];
```

Rendered as-is, these are three labelled buttons that do nothing. Both panels
also fall back to a `PanelPlaceholder` — the code panel's Browser tab reads
"Browser preview", the gallery's Styles tab reads "Style presets" — centred grey
text implying a feature that does not exist. `actions` and `browser` /
`stylePresets` must both be passed explicitly.

The same applies to the composer: `ComposerPanelProps.addMenu` defaults to
`COMPOSER_PANEL_ADD_MENU` ("Goal", "Plan mode", "Documents", "Spreadsheets",
"Presentations", "Code blocks") and `permissions` to `COMPOSER_PANEL_PERMISSIONS`
("Auto", "Manual", "Plan mode", "Bypass all"). Neither describes Alia. `addMenu:
[]` hides the add button, and `ComposerPanelBase.tsx` guards the permission
trigger with `permissions.length > 0` too — so `permissions: []` hides it as
well, although only the `addMenu` escape is documented on the type.
`ComposerStatusBarProps` is opt-in throughout (`branch`, `folders`, `mode`,
`context` each hide when omitted), so the template's `Main` / `context={57}` are
avoidable.

### 8. No layering slot for `AmbientField` — CONFIRMED

`AiChatContainer` paints its own opaque surface on its root `View`:

```tsx
<View testID={testID} style={[{ height: '100%', minWidth: 0, flex: 1,
  flexDirection: 'column', overflow: 'hidden',
  borderRadius: CONTAINER_RADIUS,
  backgroundColor: palette.secondary }, style]}>
```

`AiChatShell` does the same with `backgroundColor: palette.full`. Its slots are
`sidebar`, `mobileSidebar`, `children`, and `panel: (width) => ReactNode` — none
of which sits behind the chat content. `AiChatContainer`'s slots are `header`
(above the breadcrumb), `children` and `composer`. `style` reaches only the outer
`View`, and the `backgroundColor` in the base array is overridable by a later
`style` — but doing so would make every inner surface transparent at once, with
no control over which layers keep their paint.

The nearest thing to a layering contract in the whole package is in a different
family:

```ts
export interface ChatBackgroundProps {
  variant?: ChatBackgroundVariant;   // 'plain' | 'pattern' | 'gradient' | 'image'
  colors?: string[];
  /** The transcript. Drawn above the wallpaper. */
  children?: ReactNode;
```

That is the right *shape* — content above a background — but the background is
one of four built-in variants, not a caller-supplied node, so Alia's animated,
audio-reactive `AmbientField` cannot be passed to it either.

The Bloom change needed is a background node slot on `AiChatShell` /
`AiChatContainer`, with the internal surfaces made transparent by opt-in. Reading
into the container with web selectors, or forking it, is what issue §2 rules out.

### 9. `ModelPicker` welds an effort axis to the model list — FOUND DURING ADOPTION

Not in #608's list, and the one gap found by trying to adopt rather than by
reading. `ModelPicker` is the picker the matrix and the issue both bless,
because its identity contract is right: `{id, name}`, `onValueChange(modelId)`,
no display-name matching. That part is correct.

Its effort axis is not separable from it. `ModelPickerBase` renders `EffortMenu`
on the checked row **unconditionally**, indexing `effortLevels`, and
`EffortSlider` computes `max = levels.length - 1`.

Alia's levels are per-entry `capabilities.reasoningLevels`, and
`lib/hooks/use-catalogue.ts` says what that usually holds:

> Empty is the common answer: a routing profile fanning out over seventeen
> deployments offers a level only if all seventeen can send it.

So for the default selection, `effortLevels` is `[]` — and the picker draws an
empty chip with a chevron over a slider that can never commit. A control wired
to nothing, in the common case, which is what #608 §1.6 forbids.

There is a second half. `effort?: number` cannot express what Alia's store says
with `null`: no level chosen, the parameter omitted, the model decides. Adopting
the prop would turn the absence of a choice into the appearance of one.

What Bloom would need: `EffortMenu` conditional on `effortLevels.length > 0`,
and an effort value that can be absent. Until then Alia composes the model rows
itself and keeps the two axes genuinely separate.

### 10. `AiChatShell` cannot express a collapsed sidebar — CLOSED in 3.3.0

`AiChatShell` composes sidebar, workspace and right panel with a resize handle
and mobile drawers, and is the obvious answer to #608 §5. Adopting it would
cost Alia two things, and neither has a prop that recovers them.

**A collapsed desktop rail.** Alia narrows its sidebar to a 56px icon rail
through `sidebarOpen` in the UI store; `app/(app)/_layout.tsx` sets
`drawerStyle.width` to 56 or 255 and the sidebar renders icon-only rows at that
width. `AiChatShellProps` has `sidebar`, `mobileSidebar` and three widths — all
three for the PANEL. The sidebar is either in flow above `lg` or a push drawer
below it. There is no third state and no width to give it.

**The accessibility fix in #532.** `DrawerSidebar` takes the sidebar out of the
tab order and the screen-reader tree while the drawer is closed, because
react-native-drawer-layout keeps the subtree mounted and merely translates it
offscreen. That guard reads `useDrawerStatus`, which exists only because the
drawer belongs to the router. Replacing the router's drawer replaces the signal
the fix is built on.

Both are closed. Bloom 3.3.0 added `sidebarWidth`, `sidebarCollapsed` and
`collapsedSidebarWidth` (default 56 — Alia's rail width exactly), and exported
`useAiChatShell()` with `navPresented`, which is the signal the #532 guard
needed. `AiChatShell` is the app's shell now, and since Bloom 4.14.1 it guards
the closed drawer itself: `inert` on web — the one attribute covering focus, tab
order, assistive tech and find-in-page at once — and the VoiceOver/TalkBack
flags on native. Alia's own `NavRegion` wrapper went with that.

Two things did not survive the move, and neither has a Bloom contract yet:

- **Swipe-to-open.** `expo-router`'s `Drawer` had `swipeEnabled`; `AiChatShell`
  has no edge gesture.
- **The rail's collapse animation on web.** `drawerStyle` carried
  `transition: width 300ms`; the shell sets that column's width inline and its
  `style` prop reaches only the shell root, so there is no hook for it.

### On the AI Chat template

Issue #608 names `templates/ai-chat/AiChatTemplate.tsx` as the primary

### What #608 still asks for

Stated as remaining work rather than left implied. None of it is blocked by
anything above; all of it is larger than one change.

- **The shell is adopted.** `AiChatShell` replaced the `expo-router` `Drawer`,
  and the sidebar is COMPOSED from Bloom's parts (`SidebarItem`,
  `SidebarFolder`, …) rather than swapped for the closed `<Sidebar>`, which has
  no `children` and no slots and would have dropped the conversation context
  menu, project and folder management, the history's infinite scroll and date
  grouping, hover prefetch, the referral banner and the footer's unread badge.
  What Bloom has a part for uses Bloom's; the rest stays Alia's, with the
  missing contract named in gap 10.

  One consequence is a product decision, not a defect: Bloom holds the nav in
  flow only from `lg` (1024) while Alia's was in flow from 768, so tablet
  portrait now gets a drawer and a full-bleed chat. The visual baseline records
  it as a failure at 768 deliberately, pending that decision.
- **The timeline** is `AiChatThread`: its `followThreshold`, `onStartReached`
  and `maintainStartPosition` replaced `use-scroll-to-bottom.ts`, and a cursor
  jump measures its row and calls `scrollToOffset`. Bloom still has no
  virtualization and no `scrollToIndex`, and `VirtualList` cannot host the
  thread (`onEndReached` fires at the END while Alia pages UPWARD, and
  `maintainVisibleContentPosition` is ignored on web). So long threads are
  WINDOWED in Alia (`lib/hooks/use-timeline-window.ts`): the newest 40 rows
  mount and older ones are revealed a page at a time through the same anchored
  `onStartReached` growth history paging uses — measured, and its limits
  stated, in [the runtime baseline](./runtime-baseline.mdx#9-the-timeline-at-1000-and-5000-messages).
  The same hook restores each conversation's position. Day lines are Bloom's
  `ChatDateHeader` inline, and thread seams a labelled `Divider`.
- **The composer** is done, as composition rather than adoption: `ComposerLoader`
  is reused directly, Bloom's Enter rule is reimplemented over Alia's own field,
  and `ComposerPill`, `ComposerPanel`, `ModelPicker`, `ComposerAttachments`,
  `ComposerStatusBar` and `ControlSurface` were each declined with the loss
  named — see gaps 1, 2, 5 and 9. What remains is attachments: drag-and-drop and
  retry do not exist in Alia today, and Bloom has no contract for real upload
  progress to adopt.
- **Attachments.** `ComposerAttachments` simulates its uploads (gap 5). Real
  progress, error, retry and cancel have no Bloom contract to adopt.
- **The feature-boundary tree** in #608 §4 — `features/{chat,voice,agents,…}/
  {model,runtime,ui}`. `lib/chat/` is its beginning, not the whole of it.
  `components/ui/` remains a second design layer beside Bloom's.
- **§13's visual comparison, for the chat itself.** The welcome screen and the
  ambient field now have a reproducible reference (see
  [the visual baseline](./visual-baseline.mdx)). The conversation, dictation,
  playback and call references #608 §3.1 also asks for remain uncaptured: each
  needs authentication and a live API, and none was faked to fill the row.
- **§12 runtime performance.** The bundle baseline exists and says something
  uncomfortable: `index-*.js` is 10,528,839 B, 93% of all JS, against 752,652 B
  spread over 47 lazy route chunks. Code splitting exists in name only. Runtime
  cost — time to interaction, render and JS cost while streaming, memory — is
  still unmeasured; the capture harness pins the animation clock precisely so
  that timings cannot be read off it, so that needs a second harness.
- **Native.** No iOS or Android run. Bloom documents different blur and mask
  backends there, so the web baseline does not transfer.
