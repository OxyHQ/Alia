# Chat runtime

`POST /alia/chat` and `POST /v1/chat/completions` enter the same Alia product
runtime. Alia owns authentication, entitlements, conversations, memory, agents,
tools, approvals, research, prompts and product stream events. Hosted inference
is delegated to Kaana.

## Identity

The request `model` field names either an exact Alia product routing identifier
such as `kaana-v1`, or a concrete `<publisher>/<model>[@<revision>]` reference.
The identifier is matched by exact string equality, never by display name,
database order or a first-row fallback. Alia translates an accepted public
profile through the reviewed closed map in
`packages/api/src/config/oxy-inference-routing-profile-ids.ts` and sends Oxy its
opaque routing-profile primary key as `routingProfileId`. Oxy validates that
exact row before building the Kaana v2 envelope; Kaana never receives or looks
up the product spelling. A routing profile is a policy choice, not an
Alia-branded model and not a provider alias. Removed `alia-*` identifiers are
unregistered; there is no translation or deprecation shim for them.

User-owned runtimes are a separate explicit path. Their user-supplied model and
credential never join Kaana's hosted credential pool.

## Hosted request path

1. Auth resolves the Oxy user or application credential.
2. `buildChatRequestContext` validates the requested identity, entitlement,
   product mode and capabilities, then reserves product credits.
3. Alia assembles conversation context, memory, agent instructions and tools.
4. The inference seam calls `@oxyhq/core`'s `OxyInferenceClient` with an exact
   opaque `routingProfileId` or concrete model and Alia's service credential.
5. Oxy authenticates that credential and resolves routing policy into ordered
   `authorizedRoutes`, signs the final envelope, and sends it to Kaana.
6. Kaana executes only those authorized deployments, streams contract events
   and emits metered usage.
7. Alia translates the result into its product stream, persists the turn and
   finalizes product accounting.

Alia never constructs `authorizedRoutes`, signs an edge envelope or calls a
Kaana URL. Those are Oxy-owned responsibilities. No provider, deployment,
region or permissive fallback may be invented in Alia.

## Request shape

```json
{
  "model": "<kaana-routing-profile-id>",
  "messages": [
    { "role": "user", "content": "Prepare my meeting with Sarah" }
  ],
  "stream": true,
  "conversationId": "conv_…",
  "reasoningEffort": "medium",
  "agentMode": "research",
  "deepResearch": true,
  "fallbackPolicy": "cross-model",
  "tools": ["webSearch", "webScraper"],
  "stream_options": { "include_usage": true }
}
```

The profile expresses intent. Oxy and Kaana own route authorization and
execution; Alia never sees an upstream-provider key.

## Product stream events

Standard OpenAI-compatible chunks are emitted beside Alia product events. The
`alia.*` namespace belongs to the product runtime, not to Kaana's generic
inference contract. Active event families include plan previews, model/profile
switches, reasoning, tool results, delegated-agent output, agent-session state,
titles and research progress.

Approval requests/results use the authenticated Socket.IO agent-session room,
not the HTTP SSE connection. Clients must not wait for them on the completion
stream.

## Persistence and failure

Conversations and messages are stored through the Postgres repositories. Usage
records persist the requested identity separately from the routing profile that
served it. Provider/deployment detail remains internal to the Oxy/Kaana receipt
and must not be exposed through Alia responses or errors.

If Oxy or Kaana is unavailable, hosted inference fails visibly with the typed
product error. Alia does not fall back to an in-process provider adapter.

## Automation control plane

`/automations` is the normalized structured control plane. `/triggers` remains
available for legacy routines; both scheduled row types use the same elected
scheduler.
