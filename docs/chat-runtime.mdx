# Chat runtime

`POST /alia/chat` and `POST /v1/chat/completions` enter the same Alia product
runtime. Alia owns authentication, entitlements, conversations, memory, agents,
tools, approvals, research, prompts and product stream events. Hosted inference
is delegated to Kaana.

## Identity

The request `model` field is a real `<publisher>/<model>` from Oxy's catalogue
(`GET /catalogue`), or absent for the person's default model
([ADR 0012](./adr/0012-alia-uses-real-models.md)). Alia checks it against the
cached catalogue and sends it to Oxy unchanged as `model`. An id the catalogue
does not carry — including the retired `mode:*` and `route:*` spellings — is
refused `400 model_not_found` with `param: "model"` before credits are reserved.
Alia has no models, modes or routing profiles of its own, and never substitutes
another model for the one requested.

User-owned runtimes are a separate explicit path. Their user-supplied model and
credential never join Kaana's hosted credential pool.

## Hosted request path

1. Auth resolves the Oxy user or application credential.
2. `buildChatRequestContext` resolves the model (or the person's default),
   validates `reasoningEffort` against it, then reserves product credits.
3. Alia assembles conversation context, memory, agent instructions and tools.
4. The inference seam calls `@oxy.so/core`'s `OxyInferenceClient` with the
   `model`, `reasoning: { effort }` when requested, and Alia's service credential.
5. Oxy authenticates that credential and resolves routing policy into ordered
   `authorizedRoutes`, signs the final envelope, and sends it to Kaana.
6. Kaana executes only those authorized deployments, streams contract events
   and emits metered usage.
7. Alia translates the result into its product stream, persists the turn and
   charges credits from the model's catalogue prices and the metered units.

Alia never constructs `authorizedRoutes`, signs an edge envelope or calls a
Kaana URL. Those are Oxy-owned responsibilities. No provider, deployment,
region or permissive fallback may be invented in Alia.

## Request shape

```json
{
  "model": "<publisher>/<model>",
  "messages": [
    { "id": "5c2e…", "role": "user", "content": "Prepare my meeting with Sarah" }
  ],
  "stream": true,
  "conversationId": "conv_…",
  "assistantMessageId": "0b0f…",
  "reasoningEffort": "medium",
  "agentMode": "research",
  "deepResearch": true,
  "tools": ["webSearch", "webScraper"],
  "stream_options": { "include_usage": true }
}
```

`reasoningEffort` (`low` | `medium` | `high`) is accepted only when the model
lists that level in its `reasoningEfforts`. Oxy and Kaana own route authorization and
execution; Alia never sees an upstream-provider key. There is no per-request
fallback parameter: a body carrying `fallbackPolicy` (or `fallback_policy`) is
refused with `400 invalid_request` before any credit is reserved, because the
public Oxy inference request has no such field and Oxy resolves routes from the
application's routing policy (`lib/chat/request-context.ts`).

## Product stream events

Standard OpenAI-compatible chunks are emitted beside Alia product events. The
`alia.*` namespace belongs to the product runtime, not to Kaana's generic
inference contract. Active event families include plan previews, reasoning, tool results, delegated-agent output, agent-session state,
titles and research progress.

Approval requests/results use the authenticated Socket.IO agent-session room,
not the HTTP SSE connection. Clients must not wait for them on the completion
stream.

### Reading the stream from a server: `@alia.onl/server`

`packages/alia-server` is the supported reader for a backend that calls Alia
itself. It is NOT the SDK: no React, no DOM beyond `fetch` and
`ReadableStream`, compiled ESM and CommonJS, Node 22+.

It exists because the wire carries five shapes — OpenAI chunks, `alia.*` named
events, synthetic recovery chunks with `alia_meta`, an in-stream `{"error":…}`
payload written by `SSEWriter.writeError`, and `data: [DONE]` — and a
hand-rolled reader typically handles two. The error payload is the one that
costs: a reader with no branch for it reports an empty answer, and the code the
route already knew never reaches anyone. The package makes each shape a typed
event over a closed union, so a consumer can be wrong about what to DO with an
error and cannot fail to see one.

Its fixtures are generated by `lib/streaming-helpers.ts`, `lib/chat/sse-writer.ts`
and `lib/sse-emitter.ts` — the API's own writers, imported across the workspace
boundary — so a change to what this route emits fails that package's tests in
the same commit rather than in a consumer's logs later.

## Browser origins and `@alia.onl/sdk`

The two mounts differ in who a browser may be. `/alia/chat` takes Alia's
exact-origin CORS allowlist (`packages/api/src/lib/cors-origins.ts`, mounted
in `packages/api/src/index.ts` for every path that is not `/v1`), so a
preflight from an origin Alia does not enumerate gets no
`access-control-allow-origin`; `/v1/*` answers `*`. A request with no `Origin`
header — a server, a native app — is subject to neither. The policy is pinned
by `packages/api/src/middleware/__tests__/chat-origin-policy.test.ts`.

That is why `@alia.onl/sdk`, a product client that switches on the `alia.*`
events above, still sends its turns to `/v1/chat/completions`: it ships raw
source and compiles into apps on their own origins. An external product uses
it through its own backend today — `useAliaChat({ apiUrl })` at that backend,
which calls `POST /alia/chat` server-to-server with the user's Oxy token
forwarded and relays the SSE body unchanged (`packages/alia-chat/README.md`).

Neither mount is going away. Under
[ADR 0010](./adr/0010-alia-keeps-a-product-api-credentials-come-from-oxy-console.md)
`/v1/*` is Alia's permanent product API, so the SDK's consumers are not sitting
on a surface with a removal gate. What the relay is waiting on is the origin
registry: a third-party application's browser origins are registered on its
application in Oxy Console (OxyHQ/oxy#972), and once that exists the
per-application list replaces the `/v1` wildcard on both mounts — by changing
the pinned test on purpose, not by widening `lib/cors-origins.ts`. Issue #244
closed on that decision.

## Persistence and failure

Conversations and messages are stored through the Postgres repositories.

A stored message keeps the id the client drew it under, in
`messages.client_message_id`, and that is the id `GET /conversations/:id`
returns and the per-message routes address (`PATCH
/conversations/:id/messages/:messageId/vote`, `POST /v1/audio/speech` with
`conversationId` and `messageId`). A client that wants to address a reply it
is still showing sends each message with its `id` and names the reply it is
drawing in `assistantMessageId`; a delegated agent's answers in that turn are
stored as `<assistantMessageId>-agent-<n>`, in the order their `alia.agent`
events arrived, because that event carries no id of its own. A message sent
without an id is named by its position, `msg-<seq>`. A malformed
`assistantMessageId` (not a string of 1–128 characters) is refused with `400
invalid_request`. A turn is stored when it completes, so a failed turn has no
row to address.

Usage records persist the requested model and the revision-pinned model reference that
served it. Provider/deployment detail remains internal to the Oxy/Kaana receipt
and must not be exposed through Alia responses or errors.

If Oxy or Kaana is unavailable, hosted inference fails visibly with the typed
product error. Alia does not fall back to an in-process provider adapter.
Background derivations follow the same rule: they make one Oxy request and do
not retry an identical request locally. An Oxy routing refusal is a `503`, an
empty or invalid upstream result is a `502`, and a safe Oxy request ID is kept
for correlation without exposing provider or deployment details.

Streaming error events retain Oxy's exact error code, retryability, retry delay
and request ID through the AI SDK adapter. The product maps the typed code
before considering free-form messages or HTTP status. In particular, a platform
provider billing/credential refusal remains a non-retryable service failure;
it must not become a customer quota/authentication error or suggest that an
identical retry will repair the platform account. Failure logs pair the Alia
chat reference with the Oxy error/request ID for incident correlation.

## Automation control plane

`/automations` is the normalized task control plane. Conversation can create a
future assistant task with no connected-app action, or connected work with exact
Oxy authority. Creation never runs the task; a separate Run now operation does.
