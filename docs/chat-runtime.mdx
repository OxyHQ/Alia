# Chat runtime

`POST /alia/chat` and `POST /v1/chat/completions` enter the same Alia product
runtime. Alia owns authentication, entitlements, conversations, memory, agents,
tools, research, prompts and product stream events. Hosted inference
is delegated to Kaana.

## Identity

The request `model` field is a power level (`auto` … `ultra`, sent to Oxy as
`routingProfile`; [ADR 0014](./adr/0014-people-choose-power-levels-not-models.md)),
a real `<publisher>/<model>` from Oxy's catalogue (`GET /catalogue`), or absent
for `auto` ([ADR 0012](./adr/0012-alia-uses-real-models.md)). Alia checks a model
against the cached catalogue and sends it to Oxy unchanged as `model`. An id the catalogue
does not carry — including the retired `mode:*` and `route:*` spellings — is
refused `400 model_not_found` with `param: "model"` before credits are reserved.
Alia has no models, modes or routing profiles of its own, and never substitutes
another model for the one requested.

User-owned runtimes are a separate explicit path. Their user-supplied model and
credential never join Kaana's hosted credential pool.

## Hosted request path

1. Auth resolves the Oxy user or application credential.
2. `buildChatRequestContext` resolves the level or model (absent is `auto`),
   validates `reasoningEffort` against it, admits the turn's attachments (the
   agent's feature gates are checked, `file` parts are read from Oxy Files as the
   person, gated parts are spent — [Embedding an agent](./agent-embedding.md) §5),
   then reserves product credits. A refused attachment reserves nothing.
3. Alia assembles conversation context, memory, agent instructions and tools.
4. The inference seam calls `@oxy.so/core`'s `OxyInferenceClient` with the
   `model`, `reasoning: { effort }` when requested, and Alia's service credential.
5. Oxy authenticates that credential and resolves routing policy into ordered
   `authorizedRoutes`, signs the final envelope, and sends it to Kaana.
6. Kaana executes only those authorized deployments, streams contract events
   and emits metered usage.
7. Alia translates the result into its product stream, persists the turn and
   charges credits from the model's catalogue prices and the metered units.

Alia never constructs `authorizedRoutes`, signs an edge envelope or calls a
Kaana URL. Those are Oxy-owned responsibilities. No provider, deployment,
region or permissive fallback may be invented in Alia.

## Request shape

```json
{
  "model": "<publisher>/<model>",
  "messages": [
    { "id": "5c2e…", "role": "user", "content": "Prepare my meeting with Sarah" }
  ],
  "stream": true,
  "conversationId": "conv_…",
  "assistantMessageId": "0b0f…",
  "reasoningEffort": "medium",
  "deepResearch": true,
  "tools": ["webSearch", "webScraper"],
  "stream_options": { "include_usage": true }
}
```

`reasoningEffort` (`low` | `medium` | `high`) is accepted only when the model
lists that level in its `reasoningEfforts`. Oxy and Kaana own route authorization and
execution; Alia never sees an upstream-provider key. There is no per-request
fallback parameter: a body carrying `fallbackPolicy` (or `fallback_policy`) is
refused with `400 invalid_request` before any credit is reserved, because the
public Oxy inference request has no such field and Oxy resolves routes from the
application's routing policy (`lib/chat/request-context.ts`).

## Product stream events

Standard OpenAI-compatible chunks are emitted beside Alia product events. The
`alia.*` namespace belongs to the product runtime, not to Kaana's generic
inference contract. Active event families include plan previews, reasoning, tool results, delegated-agent output, agent-session state,
titles and research progress.

There are no approval events on either transport: no agent asks for approval
(ADR 0020 §3). A tool effect runs under the actor's Oxy authority, or Oxy refuses
it and the model is told `oxy_app_unavailable`.

### Reading the stream from a server: `@alia.onl/server`

`packages/alia-server` is the supported reader for a backend that calls Alia
itself. It is NOT the SDK: no React, no DOM beyond `fetch` and
`ReadableStream`, compiled ESM and CommonJS, Node 22+.

It exists because the wire carries five shapes — OpenAI chunks, `alia.*` named
events, synthetic recovery chunks with `alia_meta` (older servers only; a
failed turn is now always an error), an in-stream `{"error":…}`
payload written by `SSEWriter.writeError`, and `data: [DONE]` — and a
hand-rolled reader typically handles two. The error payload is the one that
costs: a reader with no branch for it reports an empty answer, and the code the
route already knew never reaches anyone. The package makes each shape a typed
event over a closed union, so a consumer can be wrong about what to DO with an
error and cannot fail to see one.

Its fixtures are generated by `lib/streaming-helpers.ts`, `lib/chat/sse-writer.ts`
and `lib/sse-emitter.ts` — the API's own writers, imported across the workspace
boundary — so a change to what this route emits fails that package's tests in
the same commit rather than in a consumer's logs later.

## The client runtime

One conversation runtime serves every first-party client: the bottom sheet and `AliaChatScreen`
from `@alia.onl/sdk`, and the Alia app. It lives in `packages/alia-chat/src/runtime` and is
layered so each layer depends only on the ones before it:

1. **Transport** — `api.ts` (REST over the signed-in Oxy client: token, refresh and the single
   401 replay are Oxy's) and `use-conversation-stream.ts` (the `/v1/chat/completions` SSE stream).
2. **Model and state** — `types.ts`, `thread/*` (what a list of messages becomes: timeline,
   thought steps and sources, tool cards, day lines, export), `turn-failure.ts` and
   `usage-limit-error.ts` (a turn that did not answer is a typed error that keeps the person's
   turn with a retry, never a filler message), React Query keys and cache (`conversations.ts`),
   and the zustand stores (`composer-draft-store.ts`, `conversation-store.ts`).
3. **Hooks** — `useConversations`, `useConversation`, `useConversationThread`
   (send/edit/regenerate/retry/stop/clear), `useStartConversation`, `useTurnEdit`.

What differs between the sheet and the app is only the `AliaRuntimeHost` they pass to
`AliaRuntimeProvider` (navigation, credits, memory, artifacts panel, agent rows, where the work of
a turn is shown) and what they put around the conversation (see below). A voice call
always lives in a conversation: the open one, or one made when the call starts, opening on the
screen that shows it (`lib/voice-call-request.ts`). The full API, with examples for both, is in
`packages/alia-chat/README.md`.

### The conversation screen is the SDK's too

The bottom sheet, `AliaChatScreen` and the Alia app are frames around ONE screen, `AliaChatContent`
(`packages/alia-chat/src/components`). Above the runtime it has two more layers:

4. **Hooks of what a person does** — `useChatComposer` (the draft, sending, rewriting a sent
   question, suggestions, the field's keys), `useChatVoice` (the call, its sounds and its
   transcript in the thread), `useThreadView` (the present or a moment of an agent's thread),
   `useOpenThought`, `useReadAloud`, `useMessageVote`, `useThreadRows`, `useTimelineWindow`.
5. **UI** — `AliaThread` (the turns: Bloom's AI Chat turns, the work log, cards, the failed
   turn's toast, day lines, the window over a long history), `ThoughtPanel`, the composer, the
   voice call bar, `AliaChatContent` itself.

What the app keeps is what only it has: the sidebar (which reads the runtime's lists), the right
panel and the column layout that mounts them, its routes, and its callbacks. They reach the screen
through data and places, never through a second implementation: `conversationId`, `threadHandle`,
`model`/`onModelChange`/`deviceModels`, `addMenu`, `chrome`, `voice`, `renderUsageLimit`, and the
host members `showThought`, `openAutomation`, `faviconUrl`. `packages/app/src/features/chat` is the
inventory of that (see `docs/app-architecture.mdx`), and
`packages/alia-chat/tests/components/thread/one-thread.test.tsx` holds that the sheet and the app
draw the same rows and that nothing else imports Bloom's thread.

**The work of a turn** has two halves with a seam between them. The thread selects a turn
(`useThoughtStore`: message, tab and the conversation it belongs to) and tells the host
(`showThought('pressed' | 'automatic')`); the host decides where `ThoughtPanel` is drawn (the app:
its right panel; the sheet: a sheet over the conversation) and tears the selection down when it
closes. A host without `showThought` has no panel and the "Worked for…" line is plain text.

**Tool cards** — weather, market quote, FairCoin price, scheduled task — are the SDK's, not the
app's. The tools behind them (`getWeather`, `getMarketQuote`, `getFairCoin`) are part of the
pipeline every Alia surface calls (`lib/tool-pipeline.ts`, on the `web` grant), and the card's
numbers are in the stored message, so a surface that draws Alia's reply draws them. The one
difference is the scheduled task: it points at a screen only the host has, so it is a link only
where the host passes `openAutomation`.

**Power levels** (ADR 0014) are the SDK's: `POWER_LEVELS`, `buildPowerLevelOptions` and the
selector in the composer, on every surface that lets the person choose. Which of the person's own
devices run a model (`local/…`) is the host's, handed in as `deviceModels`. The add menu stays
the host's: web search, deep research, skills and connected apps are rows with plan
gates, a router and a library behind them, so the SDK offers the slot (`addMenu`) and photos by
default.

## Browser origins and `@alia.onl/sdk`

The two mounts differ in who a browser may be. `/alia/chat` takes Alia's
exact-origin CORS allowlist (`packages/api/src/lib/cors-origins.ts`, mounted
in `packages/api/src/index.ts` for every path that is not `/v1`), so a
preflight from an origin Alia does not enumerate gets no
`access-control-allow-origin`; `/v1/*` answers `*`. A request with no `Origin`
header — a server, a native app — is subject to neither. The policy is pinned
by `packages/api/src/middleware/__tests__/chat-origin-policy.test.ts`.

`@alia.onl/sdk` is a product client that switches on the `alia.*` events above, and it is
embedded by every Oxy app on that app's own web origin. So it speaks **only to `/v1`** — a bearer
of the person's Oxy session, no cookies, public CORS: turns go to `POST /v1/chat/completions` (the
handler `/alia/chat` mounts) and conversations to `/v1/conversations`. The conversations router is
the same one `/conversations` mounts, behind a person's session alone: an application key, a
channel-bot or Telegram secret is refused, because a conversation is
somebody's private history. `tests/runtime/v1-only.test.ts` in the SDK fails on any URL the
transport builds outside `/v1`, and `v1-conversations-auth.test.ts` and `chat-origin-policy.test.ts`
in the API pin the door and the preflight. `/conversations` and `/alia/chat` keep serving Alia's own
clients (the integrations service uses `/conversations` with its channel-bot secret).

Neither mount is going away. Under
[ADR 0010](./adr/0010-alia-keeps-a-product-api-credentials-come-from-oxy-console.md)
`/v1/*` is Alia's permanent product API, so the SDK's consumers are not sitting
on a surface with a removal gate. What a per-application origin policy is waiting on is the origin
registry: a third-party application's browser origins are registered on its
application in Oxy Console (OxyHQ/oxy#972), and once that exists the
per-application list replaces the `/v1` wildcard on both mounts — by changing
the pinned test on purpose, not by widening `lib/cors-origins.ts`. Issue #244
closed on that decision.

## Tool budget and the tool loader

One inference request carries at most **128 tools**: the Oxy edge's `tools`
maximum (`OxyHQServices packages/api/src/schemas/inferenceEdge.schemas.ts`),
which mirrors OpenAI's own per-request maximum. Alia names it once,
`MAX_TOOLS_PER_INFERENCE_REQUEST` in `lib/inference/tool-limit.ts`, and fits
inside it; the limit does not grow. Their definitions also share the request's
byte budget with the conversation (next section).

It is enforced twice:

- **`ToolPipeline.forUser`** (`lib/tool-budget.ts`) never lets a request carry
  more. Every path that runs a model with tools — chat streaming and
  non-streaming, the autonomous runner, `consultAgent` turns, Telegram
  bot turns (`routes/webhooks.ts`) and service-token triggers
  (`routes/internal.ts`) — assembles through it and spreads its `routing`
  beside `tools`.
- **The Kaana adapter** (`kaana-language-model.ts`) refuses a request with more
  than 128 tools before sending, with a typed `ToolLimitExceededError`
  (`invalid_request`, `param: "tools"`, not retryable) and a log naming the
  tool families. The edge's 400 is unreachable from Alia.

When a turn's tools fit (count AND bytes), nothing changes. When they do not,
the tools of connected apps — each Oxy service (`oxy_<app>__*`), each MCP
server (`mcp_<server>__*`) and each OAuth integration — are **deferred and
loaded by the model, one tool at a time**:

1. The first step sends the core tools (clock, built-ins and artifacts, memory
   and messaging, runtime primitives, skills, agent tools, and every tool the
   client sent) plus one tool, `loadTools({ names?, query?, limit?, unload? })`.
   The system prompt's **Tools from the person's apps** section is the
   catalogue: every app with its tool count, what it covers (the subject words
   of its own tool names, derived, never a list kept in Alia) and the **name of
   every tool** — the prefix once per app, no definitions. It tells the model
   its access is real, that a request in any language or by any synonym maps to
   an app by meaning, and that it must load tools before saying it cannot reach
   something an app covers. A routed turn omits the "Connected Oxy Services"
   tool-name list, which named tools that were not yet in the request.
2. `loadTools` marks tools loaded; from the next step their real definitions
   are in the request (AI SDK `prepareStep` → `activeTools`). The model loads
   by **exact name** (the full name, or the bare part under the app's prefix
   when it is unambiguous) or by **intent**: `query` ranks every deferred tool
   by name words, app words and description and loads the best `limit`
   (default 5, at most 10). The model then calls the tools directly. The full
   tool set stays registered, so execution, authorization, the
   runtime policy, result truncation and tool-name mapping are exactly those of
   a direct call — there is no proxy tool.
3. The unit is the tool, never the app: Mention's 94 tools are not "too big to
   open", the model loads the five a request needs. The result is meant to be
   acted on: `loaded` (with each description), `alreadyLoaded`, `unloaded`,
   `unknown` (with `didYouMean`), `notLoaded` with a reason (`tool_limit` /
   `size_limit`: unload something and ask again, with `unloadCandidates`;
   `picks_fill_request`: the person's picks hold the room; `too_large`: it can
   never fit on this model), `capacity` (tools and definition bytes in use and
   allowed) and a `hint` in words.

Loaded before the model asks, in this order and counted first:

- **Explicit picks** — the composer's connector pick (`mcpServerId`), a whole
  MCP server. A pick may also be one exact tool name (`pickedApps`). A pick's
  tools are loaded while they fit and the model cannot unload them; what does
  not fit stays in the catalogue and loadable by name. A pick never fails the
  turn.
- **Sticky tools** — tools the model called earlier in the conversation, read
  from the history the client replays (`toolInvocations` / `tool_calls`), most
  recent first, while they fit. A tool that was loaded and never called, or
  unloaded later (`loadTools` results are replayed), is not sticky. No column
  stores them.

A client's own tools are never deferred. More than 128 of them is refused
before credits are reserved (`lib/chat/request-context.ts`), and a set whose
always-sent tools leave no room for the loader is refused by the assembler with
the same typed error.

## Request input budget

One inference request's input is bounded in **bytes**. The Oxy edge refuses an
Alia completion whose controlled input — UTF-8 bytes of
`JSON.stringify({ input, tools, toolChoice, responseFormat })` plus 256, plus 32
per message, plus 32 per tool — is over 126_976
(`maxControlledCompletionInputBudget`, OxyHQServices
`packages/api/src/config/inferenceEconomicPolicy.ts`; measured by
`controlledInputBudget` in `packages/api/src/services/inferenceInternalPilot.ts`).
Bytes are a worst-case token bound (a token is never less than one byte), so a
request of N bytes is at most N tokens.

**One function computes the budget**: `requestInputBudgetBytes(model)` in
`lib/inference/request-budget.ts`. It is derived, not declared:

- the **model's window**: the catalogue's `maxContextTokens` less the room for
  the answer (`maxOutputTokens`, at most half the window), read as bytes — the
  pessimistic reading, which can never overflow the window. `getAIModel` passes
  the resolved model's catalogue entry to the Kaana adapter
  (`inputLimits`) and `ToolPipeline.forUser` receives the same (`inputLimits`);
- the **server's limit**: Oxy's 126_976 less a 4 KiB margin (122_880), the
  binding constraint for any model with a window of ~128K or more;
- optionally lowered (never raised) by `ALIA_INFERENCE_INPUT_BUDGET_BYTES`.

A power level (`auto`, `instant`, …) has no catalogue entry — Oxy picks the
model per request — so its budget is the server's limit. The tool definitions
may take half of the budget (`TOOL_DEFINITIONS_SHARE`); the tool loader keeps
what it sends within `toolDefinitionsBudgetBytes(budget)`. No other file holds
a byte constant.

The Kaana adapter measures every model step of every surface — chat, `/v1`,
tasks, the runner, delegation, bots, triggers and background derivations all
reach Oxy through it — exactly as Oxy will, and when the request is over,
shrinks only what is sent, in this order, until it fits:

1. **Older tool results**, oldest first, in this turn and in history: their
   content becomes `[result omitted to fit context — call the tool again if
   needed]`. The call and its id stay, so no result is orphaned. The latest
   step's results are kept.
2. **The oldest history turns**, whole (a user message and everything up to the
   next), never the system prompt, the latest user message or the current step
   chain.
3. **The latest step's results**, oldest first, never the newest.

The AI SDK's messages and what the turn persists are untouched; each step is
fitted again. If a request still cannot fit (a pasted message larger than the
budget), it is not sent: the step fails with a typed `context_length_exceeded`
(`RequestInputBudgetExceededError`, not retryable), the edge's own code, and a
log of the measured sizes — never the content.

**The server limit is Oxy configuration, and it is what makes the shrink above
fire in production.** `maxControlledCompletionInputBudget` is 126_976 for the
`alia-kaana` pilot whatever the route behind it: a model with a 1M window is
metered as if it had 128K. Alia's side is now correct for every window; the
remaining cost of that constant is that long conversations on a large-window
model are shrunk (old tool results omitted, oldest turns dropped) at ~123 KB.
If that is not wanted, the change is in OxyHQServices
`inferenceEconomicPolicy.ts` (derive the ceiling from the route's
`maxContextTokens`, or raise it for `alia-kaana`) and then
`OXY_CONTROLLED_COMPLETION_INPUT_CEILING_BYTES` here follows it — a one-line
change plus its test. Alia does not raise it on its own.

## Persistence and failure

Conversations and messages are stored through the Postgres repositories.

A stored message keeps the id the client drew it under, in
`messages.client_message_id`, and that is the id `GET /conversations/:id`
returns and the per-message routes address (`PATCH
/conversations/:id/messages/:messageId/vote`, `POST /v1/audio/speech` with
`conversationId` and `messageId`). A client that wants to address a reply it
is still showing sends each message with its `id` and names the reply it is
drawing in `assistantMessageId`; a consulted agent's answers in that turn are
stored as `<assistantMessageId>-agent-<n>`, in the order of their
`alia.agent_start` events (`docs/agent-embedding.md` §4). A message sent
without an id is named by its position, `msg-<seq>`. A malformed
`assistantMessageId` (not a string of 1–128 characters) is refused with `400
invalid_request`. A turn is stored when it completes, so a failed turn has no
row to address.

Usage records persist the requested model and the revision-pinned model reference that
served it. Provider/deployment detail remains internal to the Oxy/Kaana receipt
and must not be exposed through Alia responses or errors.

If Oxy or Kaana is unavailable, hosted inference fails visibly with the typed
product error. Alia does not fall back to an in-process provider adapter.
Background derivations follow the same rule: they make one Oxy request and do
not retry an identical request locally. An Oxy routing refusal is a `503`, an
empty or invalid upstream result is a `502`, and a safe Oxy request ID is kept
for correlation without exposing provider or deployment details.

A turn whose inference fails ends as a failed turn, never as an answer —
whether it failed before any output (Kaana's routing and retries exhausted, the
time budget spent, a terminal upstream refusal) or after text or a tool call
already reached the client. Every such exit goes through one function, `failTurn`
in `routes/v1/chat-completions.ts`, and carries the same OpenAI-shaped envelope:

```json
{"error":{"message":"Service temporarily unavailable. Please try again in a moment.",
  "type":"server_error","param":null,"code":"PROVIDER_UNAVAILABLE",
  "retryable":true,"retryAfter":4,"reference":"chatcmpl-…"}}
```

- **Stream open** (every `stream: true` request opens it before any work, in
  `lib/chat/request-context.ts`): the envelope as one `data:` frame, then
  `[DONE]`, with no content and no stop chunk — the same way a credit or limit
  refusal is sent on an open stream.
- **Nothing sent yet** (a non-streaming request): HTTP `503` with the envelope
  when `retryable` is true, `500` when retrying cannot help, and `Retry-After`
  when the failure carries a delay — the same envelope a refusal uses.

`message` is the code's fixed product text, never the upstream's words;
`retryAfter` appears only when there is one; `reference` is the run id. `type`
is always `server_error`, and the status is never `429`/`402`/`401`, because an
upstream rate limit, billing refusal or credential failure is not the caller's
limit, plan or session. Nothing is persisted, no title is written, and the
reservation is refunded by the handler's single release point.

Before output, the route used to answer with an ordinary assistant message —
"all models are currently busy" (or Spanish, sniffed from the message) — ending
in `finish_reason: "stop"`, flagged only by `alia_meta.synthetic`. Every client
that did not know the flag showed Alia's apology as the model's answer. That
path is gone; clients still read the flag so an older server cannot slip one in.

`runStream` throws on every `error` part the tools-disabled synthesis pass does
not recover (that pass runs only when no text was streamed and tool results
exist). The provider loop returns `exhausted` with the typed `AliaError` when
nothing was streamed, and rethrows when something was; the 80s global timeout
uses `failTurn` too.

The deadlines are three, and the last one really stops the call: the streaming
first-byte clock (20s, ended by the first CONTENT chunk — `start` is not one),
an inactivity watchdog on the stream (45s of silence, held while one of Alia's
own tools runs), and the 80s global timeout, which aborts the provider call
through the route's `providerAbort`. A non-streaming call has no first byte and
gets its own 70s budget. After the global timeout nothing is stored or charged
(`assertLive` in the provider loop) and the hold is refunded.

A turn that ends with no text, no tool call and no agent answer (for example a
`length` stop spent thinking) fails typed (`EMPTY_RESPONSE`, or
`CONTENT_FILTERED`); it is not a success. `finish_reason` is OpenAI's
vocabulary (`stop`, `length`, `tool_calls`, `content_filter`). A turn is billed
on `totalUsage` (every step), summed across the tools-disabled synthesis pass.

On the clients: the app draws its failed-turn card — its own i18n line, `code ·
Ref reference` and Retry — for the frame and for the HTTP envelope alike,
keeping partial output when there was some. `@alia.onl/sdk` raises an
`AliaChatStreamError` carrying `status`, `code`, `retryable`, `retryAfter` and
`reference`; `@alia.onl/server` yields an `error` event (or throws
`AliaRequestError`) with the same fields; Codea and Cowork raise an
`AliaChatError` with `code` and `retryable`. Alia does not re-send the failed
step itself: Kaana owns retries, and the AI SDK cannot resume a multi-step run
at the step that failed.

Streaming error events retain Oxy's exact error code, retryability, retry delay
and request ID through the AI SDK adapter. The product maps the typed code
before considering free-form messages or HTTP status. In particular, a platform
provider billing/credential refusal remains a non-retryable service failure;
it must not become a customer quota/authentication error or suggest that an
identical retry will repair the platform account. Failure logs pair the Alia
chat reference with the Oxy error/request ID for incident correlation.

## Automation control plane

`/automations` is the normalized task control plane. Conversation can create a
future assistant task with no connected-app action, or connected work with exact
Oxy authority. Creation never runs the task; a separate Run now operation does.
