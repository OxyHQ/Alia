# Visual baseline

[#608](https://github.com/OxyHQ/Alia/issues/608) §3.1 asks for a visual and
motion reference captured **before** the chat refactor goes further, §12 for a
reproducible performance baseline over a fixed viewport matrix, and §13 for
visual comparison evidence. All three were at zero while `packages/app`'s chat
UI was being actively rewritten.

This page is the record of what now exists. The harness is
`packages/app/scripts/visual/`; the images are committed next to it in
`baseline/`.

**Read the [honest status](#9-what-is-still-not-captured) before quoting this as
coverage.** One screen is captured. Four of #608 §3.1's six required references
are not, and cannot be from a static export.

## 1. Running it

```bash
bun run --filter @alia/app visual:baseline
```

That is the whole command. It reuses `packages/app/dist` if the export is
already there, otherwise it runs `expo export --platform web` itself (not
`setup-skia-web`: nothing on web fetches `canvaskit.wasm`); serves `dist/` from Node's own `http` on an ephemeral loopback
port; drives Chromium through `playwright-core`; and overwrites the 28 PNGs and
`manifest.json` in `packages/app/scripts/visual/baseline/`.

| Flag | Effect |
| --- | --- |
| `--check` | Capture into a temp directory and **compare** against the committed baseline instead of overwriting it. Exits non-zero on any case outside tolerance. |
| `--rebuild` | Re-export even if `dist/` exists. |
| `--only <text>` | Only cases whose file name contains `text`. |
| `--tolerance <n>` | Override the per-channel tolerance. |
| `--keep <dir>` | With `--check`: keep every capture in `dir`, and write `<case>.diff.png` beside each failing one — the reference as a grey ghost, pixels over tolerance in red (brighter = larger delta), pixels that moved within it in blue. |
| `--dist <dir>` | Capture an existing export elsewhere (another checkout, an older build) instead of `packages/app/dist`. Never rebuilds it. |
| `--engine <name>` | `chromium` (default), `firefox` or `webkit`. Chromium compares against `baseline/`, any other engine against `baseline-<engine>/` — see [§8](#8-other-engines). |
| `--smoke` | No pixels: at every §12 width, the welcome must render, log no console error of the app's own, and not scroll sideways. |

`--check` is both the determinism proof and the regression gate:

```bash
bun run --filter @alia/app visual:baseline --check
```

A full run is about nine minutes, nearly all of it the 60fps replay described
below. `dist/` is gitignored and never committed; the PNGs are (4.8 MB for all
28).

### No new dependencies

Nothing was added to any manifest but the one script entry. The harness uses
`playwright-core` (already in the tree via `packages/alia-cowork` and
`packages/integrations`, with Chromium already cached in `~/.cache/ms-playwright`)
and otherwise only `node:http`, `node:zlib` and `node:fs`. In particular there
is **no image-diff package**: `scripts/visual/png.mjs` is a ~90-line PNG reader
for the one format Chromium's screenshot encoder emits (8-bit, non-interlaced,
colour type 2 or 6) plus a channel comparison. A dependency whose entire job is
`inflate` plus a subtraction is a dependency that has to be audited and upgraded
forever.

The files are `.mjs` rather than `.ts` on purpose. `packages/app/tsconfig.json`
includes `**/*.ts`, so a TypeScript harness would put an undeclared
`playwright-core` import into `bun run --filter @alia/app typecheck`. The types
that matter are carried in JSDoc instead.

## 2. The problem: this screen never stops moving

`packages/app/components/ambient-field.tsx` is the brand gradient #608 §3.1 says
must be preserved. It is three blurred, blended SVG radial gradients that enter
on a staggered 2.4s tween and then run `withRepeat(..., -1)` float loops of
8000ms, 9500ms and 11000ms, plus a 900ms pulse. It **never settles**. "Wait a
couple of seconds, then screenshot" is not a baseline for it; it is a lottery
over the loop phase, and every re-run would look like a regression.

So the clock is owned rather than waited on.

Reanimated 4 on web steps every animation from the timestamp its
`requestAnimationFrame` callback is handed (`valueSetter.js`:
`step(timestamp)`), and takes an animation's *start* time from
`performance.now()` (`react-native-worklets`, `initializers.js`:
`_getAnimationTimestamp = () => performance.now()`). `scripts/visual/clock.mjs`
replaces both, in an init script that runs before any bundle script:

- `requestAnimationFrame` still fires on Chromium's real frames — the app keeps
  booting and rendering — but every callback receives `__visualClock.now`.
- `now` starts at **0 and stays there through boot**. This is the half that
  matters: every animation's start time is 0 regardless of how many real frames
  the machine burned loading a 10 MB bundle, so a fast host and a slow host
  start from the same instant.
- `performance.now()` and `Date.now()` read the same virtual clock, so nothing
  can sample a second, real clock behind our backs.

### Why it replays instead of jumping

The obvious move — set `now = 6000` and shoot — does not work, and it fails
*quietly*. `withDelay(400, withTiming(...))` is a delay animation that starts
its inner tween on the first frame past the delay. A single jump satisfies the
delay at t=6000 and then starts a 500ms tween **at** 6000, against a clock that
never moves again, so it sits at progress 0 forever.

This was not theoretical: the first capture at 6000ms produced a plausible-looking
screenshot of the mark and the headline with the subtitle, both buttons and the
entire body reveal missing, because `reveal`, `subtitleIn` and `ctaIn` were all
stranded at 0. It would have been committed as "the Meet Alia baseline".

`playTo(ms)` instead advances `now` by exactly one 60fps frame (16.667ms) per
real frame until it reaches the target, then stops dead. Every chained animation
gets the intermediate timestamps it needs, and the step is a constant rather
than whatever the machine managed, so the replay is identical everywhere. After
the target it holds still for ten frames, because the value setter and the style
mapper are separate frames and the last animated value needs a motionless frame
or two to reach the DOM.

## 3. Everything that is pinned

| Pinned | Value | Why |
| --- | --- | --- |
| Animation clock | virtual, 16.667ms/frame, frozen at the target | The field never settles on its own; see above. |
| Capture instant | **6000ms** virtual for every still | The last blob comes to rest at 3590ms (1190ms delay + 2400ms tween). 6000 is past that and 2410ms into the float loops — a frame where the field is visibly drifting, not one where it happens to sit at its origin. |
| `Date.now()` / `new Date()` | `2026-01-01T12:00:00Z` + virtual ms | Anything that renders a date renders the same one. |
| `deviceScaleFactor` | `1` | A fractional factor resamples the 70px blur differently per machine. |
| `locale` / `timezoneId` | `en-US` / `UTC` | The headline is read from `lib/i18n/locales/en.json`; a different locale is a different picture. |
| Network | everything but the local static server is `route.abort`ed | A signed-out capture of a static bundle. Letting a font CDN or the Oxy API answer would make the baseline depend on what those returned that day. |
| Screenshot | `animations: 'disabled'`, `caret: 'hide'`, `scale: 'css'` | The virtual clock owns rAF; this covers the other half, the CSS transitions and Web Animations that NativeWind and Bloom use. |
| Browser | Chromium 149.0.7827.55 (`playwright-core` 1.61.1, headless) | Recorded in `manifest.json`. A Chromium bump is expected to move the blur and will need a re-record. |

### Waited on, not slept through

Two real signals gate every capture.

1. **The headline has finished typing.** `welcome-intro.tsx` reveals it one
   character every 55ms using `setInterval` — *real* time, which the virtual
   clock deliberately does not touch. The harness waits for the element whose
   `aria-label` equals its own `textContent`, and reads the expected string from
   `lib/i18n/locales/en.json` so the signal cannot silently rot when the copy
   changes. Then it waits on `document.fonts.ready`: text measured in a fallback
   face and reflowed afterwards is the classic non-deterministic screenshot.
2. **The body reveal has a measured height.** After the replay, the harness waits
   for a clipping box carrying a non-zero inline height. The reveal animates from
   0 to a height measured by `onLayout`, and the component writes no height at
   all until that measurement lands — so this is positive proof that the
   subtitle and both calls to action are laid out and on screen. It is exactly
   the check that would have caught the stranded-animation bug above.

There is no `waitForTimeout` anywhere in the capture path.

## 4. The tolerance, and why it is not zero

Byte equality does not work here and never will. The screen is a 70px blur over
three blended radial gradients; Chromium's blur is separable-convolution
arithmetic whose last bit depends on which tile boundaries the compositor
picked. Two runs of the identical frame agree on the composition and disagree on
the low bits of a few pixels.

Measured by capturing the whole matrix twice back to back, at
`deviceScaleFactor: 1`, same clock, same everything:

| | |
| --- | --- |
| Byte-identical cases | **24 of 28** |
| `welcome_390x844_dark_motion` | max Δ**4**, over 20 px |
| `welcome_390x844_dark_reduced` | max Δ3, over 42 px |
| `welcome_1280x800_light_reduced` | max Δ3, over 8 px |
| `welcome_390x844_light_reduced` | max Δ2, over 37 px |

42 pixels is 0.013% of the 329,160 in that frame. A third capture, checked
against the same committed baseline at ±6, came back green with the same worst
case of 4 and no case outside tolerance.

**The gate is a per-channel absolute difference of ±6, with zero pixels allowed
over it.** Two bits of headroom above the worst observed noise, 2% of the
channel range, invisible. It is not a loose gate: a moved element, a changed
design token or a different type face does not nudge a few dozen pixels by 4, it
moves thousands of pixels by tens or hundreds, and fails this on both the
magnitude and the count, which `--check` reports separately for exactly that
reason.

`compareRasters` deliberately reports `maxDelta` whether or not the case passes.
The number is the evidence: a run whose worst channel moved by 2 is the same
picture, and one whose worst channel moved by 90 is a different picture no
matter how few pixels it touched.

## 5. What was captured

28 PNGs, all of the **signed-out "Meet Alia" welcome screen** — #608 §3.2 says
it must be preserved, and it is the one meaningful surface that renders without
authentication.

The full matrix, 6 viewports × light/dark × reduced-motion/no-preference:

```
welcome_320x568_{light,dark}_{motion,reduced}.png
welcome_390x844_{light,dark}_{motion,reduced}.png
welcome_768x1024_{light,dark}_{motion,reduced}.png
welcome_1024x768_{light,dark}_{motion,reduced}.png
welcome_1280x800_{light,dark}_{motion,reduced}.png
welcome_1440x900_{light,dark}_{motion,reduced}.png
```

The widths are #608 §12's (320, 390, 768, 1024, 1280, 1440); the heights are
pinned here because a screenshot must have one.

**The sidebar is in frame from 1024, not from 768.** That moved when the shell
became Bloom's `AiChatShell`, whose `SIDEBAR_BREAKPOINT` is 1024; Alia's own
drawer had been in flow from 768. So tablet portrait now gets a drawer and a
full-bleed chat, with a labelled opener, the way the AI Chat template does it —
a product decision, taken deliberately, not a rendering artefact. The 768
captures were re-recorded against it.

A caveat worth carrying: these are SIGNED-OUT captures, so the composer is not
on screen in any of them. A change that replaces the composer wholesale can
leave this matrix byte-identical, as one did. This baseline speaks for the
shell, the intro and the ambient field — not for the composer.

Plus four frames of the AmbientField's own timeline, at 1280x800 light, as
motion evidence:

```
ambient_1280x800_light_motion_t01200.png   mid-entrance: one blob has arrived
ambient_1280x800_light_motion_t02400.png   the field is assembling
ambient_1280x800_light_motion_t03590.png   the last blob reaches rest
ambient_1280x800_light_motion_t09000.png   deep into the float loops
```

These four differ from each other in the gradient and are identical everywhere
else, which is the evidence that the field animates and that the clock controls
it. Capturing them at every size would multiply the matrix for no extra
information — the timeline is the same, only the frame differs.

`baseline/manifest.json` records the Chromium version, every pin, the tolerance,
the viewport list, the bundle numbers and each file's size.

### Reduced motion

`prefers-reduced-motion: reduce` is a real pass, not a copy. Reanimated reads
`window.matchMedia('(prefers-reduced-motion: reduce)')` once at module init
(`ReducedMotion.js`) and resolves every animation instantly, so the reduced
captures show the field already at rest with no float offset. Compare
`welcome_1280x800_light_reduced.png` against `..._motion.png`: **the content,
layout and brand gradient are all present** — the gradient does not vanish, it
simply does not drift. That is the §3.2 requirement evidenced rather than
asserted.

Note this is Reanimated's own behaviour. Neither `ambient-field.tsx` nor
`welcome-intro.tsx` contains a reduced-motion branch of its own.

From the same `expo export --platform web` the screenshots were taken against.

to compare *them* to.

Largest chunks:

| Chunk | Size |

`canvaskit.wasm` is a further 7.8 MB and `assets/` 2.3 MB.

This is a **bundle** baseline, not a performance baseline. See below.

## 7. Re-recorded on 2026-09-25, and why

On `a9de8f7b` the gate failed all 28 cases (worst Δ255). Nothing in the welcome
or the field had regressed; the shell around them had changed on purpose. The
evidence, with `--keep` diffs:

- **Harness determinism first.** `b360d49c`, the commit that recorded the
  baseline, re-exported and captured on the same machine, matched it
  byte for byte (Δ0 on every pixel). So the failures were changes in the app,
  not noise.
- **A linear scan** of the 32 commits on the ancestry path from `302d2f25`
  (the last one still Δ0) to `a9de8f7b` that touch `packages/app`, `bun.lock` or
  the root manifest, capturing `welcome_1280x800_light_motion` and
  `welcome_390x844_dark_motion` at each:

  | Commit | What the capture shows |
  | --- | --- |
  | `6bba6b3f` Bloom 4.11.0 (floating chrome) | the intro's words sit 11px lower — 15,871 px over tolerance |
  | `4ac6ddd1` the page scrolls the document | back where they were; only the card's bottom corner differs (23 px, Δ13) |
  | `5642ade6` Bloom 4.13.2, the card is a `ContentPanel` | the card's bottom edge changes (3,585 px, Δ68) |
  | `da1444bc` the right panel appears when the agent works | **the change in the final capture**: from 1024 up the empty "Changes / Browser" panel ("Files Alia writes in this chat appear here.") is gone and the chat card takes the whole width, so the intro re-centres in it and the field spans it; below 1024 the header loses its `</>` panel toggle. Bloom 4.13.3 in the same commit takes the card's edge off. |

  Every later commit leaves both captures identical to `da1444bc`'s.
- **The welcome and the field are unchanged where the frame is.** At 390px,
  where the card is the same size before and after, the only pixels over
  tolerance are the removed toggle and the card's corners (379 px); the
  headline, the words, the buttons and the whole gradient stay within ±6.
  Since `b360d49c`, `ambient-field.tsx` changed only a style object for the
  equal NativeWind class (`07ead06f`) and `welcome-intro.tsx` not at all.

So the baseline was re-recorded, not the code changed: the panel an empty
signed-out chat used to show was a control with nothing behind it (#608 rule
6), and its removal is the product decision `da1444bc` records.

The audit that first reported the failure also saw whole-screen differences at
320px (181,736 px over tolerance, worst at the headline) that no later run
reproduced — not from a fresh export of the same commit, and not from the
export that audit left in the main checkout, captured again with `--dist`
(343 px, the toggle). What produced them is not established.

## 8. Other engines

`--engine firefox` and `--engine webkit` run the same matrix, the same virtual
clock and the same screenshots on Playwright's Firefox and WebKit builds.

| Engine | Smoke (`--smoke`, 320–1440) | Pixels |
| --- | --- | --- |
| Chromium 149 | ✅ renders at all six widths, 0 app errors, no sideways scroll | `baseline/` |
| Firefox 151 | ✅ the same | `baseline-firefox/` — two full captures matched byte for byte (Δ0 on all 28), so it is gated like Chromium's |
| WebKit 26.5 | ❌ not run: the browser is installed but cannot start on this host without 74 Debian packages (`libgtk-4-1`, `libgraphene-1.0-0`, `libevent-2.1-7t64`, `libgstreamer-gl1.0-0`, `libgstreamer-plugins-bad1.0-0`, `libwebpdemux2`, `libharfbuzz-icu0`, `libmanette-0.2-0`, `libenchant-2-2`, `libhyphen0`, `libsecret-1-0`, `libwoff1`, …) that need `sudo … playwright-core/cli.js install-deps webkit` | none |

Every run reports 4 console errors per page that are the engine announcing a
request the harness aborted (the network is blocked on purpose); `--smoke`
counts them apart and fails only on errors whose source is the export itself.

Chromium and Firefox render the welcome with the same composition and palette
but not the same pixels — text rasterisation and the blur differ — which is why
each engine has its own baseline rather than a shared one.

## 9. What is still NOT captured

#608 §3.1 names six references. **Two are captured, four are not.**

| §3.1 reference | Status |
| --- | --- |
| Light and dark | ✅ all 6 viewports, both schemes |
| Start | ⚠️ **partial** — the signed-*out* welcome screen only. The signed-in empty chat screen is not captured. |
| Conversation | ❌ not captured |
| Dictation | ❌ not captured |
| Playback | ❌ not captured |
| Call | ❌ not captured |

The four missing ones are not an oversight and are not reachable by trying
harder with this harness. Each needs a signed-in Oxy session **and** a live Alia
API: a conversation needs `useChatConversation` to have messages, which means
`POST /alia/chat` streaming back; dictation and playback need microphone and
speech; the call UI needs a LiveKit room. The harness blocks all non-local
network by design. The conversation is now reachable in a fixtures build —
`/__fixtures/:id` renders the real chat page over a generated thread (see the
[runtime baseline](./runtime-baseline.mdx#9-the-chat-workspace-on-fixtures)) —
but only the runtime harness drives it so far; it has no pixel baseline here.

No screen was faked to fill a row in that table. An invented conversation would
be a picture of the harness, not of Alia.

Also outstanding:

- **§12 runtime performance.** What exists is the bundle size above. There is no
  time-to-interactive, no frame-rate trace, no memory figure — `playTo` replaces
  wall-clock time with a virtual clock precisely so that timings *cannot* be
  read off this run. Runtime numbers need a second harness that does not pin the
  clock.
- **Native.** iOS and Android render `ambient-field.tsx` through a different
  blur (`filter: [{ blur }]` rather than CSS `blur()`) and a different SVG
  backend. Nothing here says anything about them.
- **Interaction states.** Hover, focus rings, pressed buttons, the pointer
  parallax on the field (`onPointerMove`, ±120px) are all uncaptured; every
  still is at pointer origin.
- **The chat surfaces being refactored.** The composer, the thread, the message
  list and the Bloom migration tracked in [Bloom adoption](./bloom-adoption.mdx)
  have no visual reference at all. That is the gap #608 §13 most wants closed,
  and this page does not close it.
